# 17. CI (GitHub Actions)

## 한 줄 요약

코드를 올릴 때마다(main에 push, PR) GitHub의 **깨끗한 서버**에서 합성 데이터로 처음부터 끝까지 돌려 봅니다. 테스트 · 파이프라인 · dbt · 파이썬 결과 비교 중 하나라도 실패하면 PR에 빨간불이 켜집니다.

| 날짜 | 결정 | 이유 |
|---|---|---|
| 2026-10-21 | Phase 4를 CI부터 | Airflow · 대시보드를 붙이기 전에, 무엇을 바꿔도 전체가 깨지지 않았는지 자동으로 확인하는 장치가 먼저 있어야 함 |

| 2026-10-21 | CI 안에서도 docker compose를 그대로 | 이 PC에서 쓰는 `docker-compose.yml`을 그대로 써서 'CI에서는 되는데 내 PC에서는 안 됨'(또는 반대)을 줄임 |

| 2026-10-21 | 브랜치 → PR → CI → 합치기로 다시 | 2026-10-21에 '혼자 작업하고 바로 합치니 브랜치가 역할을 못 한다'며 main에 바로 커밋하기로 했었음. CI가 생기면서 PR마다 자동 검사가 돌아 브랜치가 다시 의미를 가짐 ([12](12_docs_and_git.md)) |

## 왜 필요했나

- 지금까지 '결과가 그대로인지'는 이 PC에서 명령을 돌려 눈으로 확인했습니다. 잊거나, PC 상태(이미 떠 있는 컨테이너, 남아 있는 파일)에 기대서 통과할 수 있습니다.
- 깨끗한 서버에서 처음부터 돌리면 '이 PC에만 있는 것'(설치된 패키지, `.env`, 지난 실행의 파일)에 기대는 문제가 드러납니다.
- Airflow · 대시보드처럼 붙일 것이 늘수록, 한 곳을 고쳐 다른 곳이 깨지는 일이 늘어납니다.

## 어떻게 했나

파일: `.github/workflows/ci.yml`

```text
코드 받기 → Python 3.14 → 패키지 설치
→ local_env (실행마다 새 계정)
→ docker compose up -d --wait  (SeaweedFS · PostgreSQL이 healthy가 될 때까지 기다림)
→ pytest 전체 (실제 저장소 · DB가 필요한 통합 테스트까지)
→ 합성 데이터로 파이프라인 (Bronze → 객체 저장소 → raw 적재 → Silver → Gold, 대사)
→ dbt build (모델 + 테스트)
→ dbt Silver · Gold = 파이썬 Silver · Gold (다르면 실패)
→ (실패했을 때만) 컨테이너 기록 남기기
```

| 설정 | 이유 |
|---|---|
| `on: push (main) · pull_request · workflow_dispatch` | 합치기 전(PR)과 합친 뒤(main) 모두 확인. 화면에서 손으로 다시 돌릴 수도 있게 |
| `concurrency: cancel-in-progress` | 같은 브랜치에 새로 올리면 앞의 실행은 취소 |
| `timeout-minutes: 30` | 무언가 멈춰도 30분 뒤에는 끝나게 |
| `--wait` | DB가 준비되기 전에 테스트가 붙어 실패하는 일을 막음 (healthcheck 활용) |
| `if: failure()` 로그 단계 | 실패한 실행에서만 컨테이너 기록을 남겨 원인을 찾기 쉽게 |

## 써 보고 확인한 것

- YAML 문법 오류를 올리기 전에 찾았습니다. `--vars "{raw_schema: raw_synthetic}"` 안의 `: `를 YAML이 '키: 값'으로 읽어서, 명령을 블록(`|`)으로 감쌌습니다.
- **아직 GitHub에서 실제로 돌려 보지 못했습니다.** PR [#2](https://github.com/seoloo/BC_Consumer_Data_Contest/pull/2)를 올렸지만 지금은 GitHub Actions를 쓸 수 없는 상태라 실행이 대기 중에 머물렀습니다(11월부터 쓸 수 있음). CI의 각 단계(local_env → compose → pytest → 파이프라인 → dbt → 비교)는 이 PC에서 같은 명령으로 모두 통과한 것을 확인했고, PR은 그 확인을 근거로 합쳤습니다. **11월에 첫 실행 결과를 확인해 여기에 덧붙입니다.**

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| 내 PC에서만 확인 | 잊을 수 있고, PC 상태에 기대 통과할 수 있습니다 |
| CI에서 단위 테스트만 | 이 프로젝트의 핵심 위험은 단계 사이 연결(파일 → DB → dbt → 비교)이라, 전체를 돌려야 의미가 있습니다 |
| GitHub의 services(DB만 따로 띄움) | 이 PC의 docker compose와 설정이 달라집니다. 같은 compose 파일을 쓰는 편이 차이가 적습니다 |
| 원본을 비밀 저장소에 두고 CI에서 사용 | 공모전 데이터는 재배포할 수 없습니다. 합성 데이터로 충분히 같은 경로를 돌 수 있습니다 |

## 스스로 점검할 질문

<details><summary>Q1. CI가 무엇이고, 이 프로젝트에서 무엇을 막아 주나?</summary>

CI(지속적 통합)는 코드를 올릴 때마다 자동으로 빌드 · 테스트를 돌려 문제가 있으면 바로 알려 주는 방식입니다. 이 프로젝트에서는 파일 → 객체 저장소 → DB → dbt → 파이썬 비교로 이어지는 연결이 깨지거나, dbt 결과가 파이썬 결과와 달라지는 것을 합치기 전에 막아 줍니다.
</details>

<details><summary>Q2. 비교 명령이 '불일치'를 출력만 하면 왜 안 되나?</summary>

CI는 명령의 종료 코드로 성공 · 실패를 판단합니다. 표에 '불일치'라고 찍혀도 명령이 정상 종료(0)하면 초록불이 켜집니다. 그래서 불일치가 있으면 종료 코드 1로 끝나게 했습니다.
</details>

<details><summary>Q3. CI에서 비밀번호 · 키는 어떻게 다루나?</summary>

이 CI의 서비스(SeaweedFS · PostgreSQL)는 실행할 때 만들어졌다가 끝나면 사라지는 일회용이라, 키도 실행마다 무작위로 만들어 그 안에서만 씁니다. 저장소에는 키를 적지 않습니다. 외부 API 키가 필요해지면 GitHub Secrets에 두고 환경변수로 넘깁니다.
</details>
