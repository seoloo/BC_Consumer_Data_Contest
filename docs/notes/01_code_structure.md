# 01. 코드 구조 · 설정

## 한 줄 요약

노트북 3개(셀 555개)를 역할별 모듈로 나눈 파이썬 패키지(`src/future_stress/`)로 옮기고, 기준값은 `config.py` 한곳에 모았습니다.

## 왜 필요했나

- **같은 코드가 여러 번 복사돼 있었습니다.** NAVER API 호출 함수는 노트북 안에서 5번 넘게 다시 정의되어 있었습니다. 하나를 고치면 나머지는 옛 버전으로 남았습니다.
- **어떤 셀이 어떤 순서로 돌아야 하는지 알기 어려웠습니다.** 셀을 건너뛰거나 순서를 바꾸면 결과가 조용히 달라졌습니다.
- **기준값이 셀마다 직접 적혀 있었습니다.** `[202601, ..., 202606]`, `0.75`, `3` 같은 숫자가 흩어져 있어서, 기준을 바꾸려면 모든 셀을 찾아야 했고 하나라도 빠지면 결과가 달라졌습니다.
- **결과표 일부를 손으로 입력했습니다.** 통계 검정표와 3개 지역 검증표의 숫자를 셀에 직접 적어 두었습니다. 계산이 바뀌어도 표는 그대로였습니다.

## 어떻게 했나

| 모듈 | 역할 |
|---|---|
| `config.py` | 경로, 분석 기간, 판정 기준값. 숫자는 여기만 고치면 됨 |
| `io_utils.py` | CSV 인코딩 자동 판별, 쉼표 숫자 변환, Parquet 저장 · 읽기 |
| `age_groups.py`, `regions.py` | 연령 · 지역 표기를 하나의 기준으로 맞추는 기준표 |
| `card_spending.py` | BC카드 정제, 연령별 소비구조, 현재 성장 지표 |
| `population.py` | 장래인구 · 주민등록인구 · 생활/유동인구 읽기 |
| `stress.py`, `diagnosis.py` | Future Stress 계산, 4유형 분류 |
| `validation.py`, `robustness.py` | 통계 검정, 민감도 분석, 생활/유동인구 보정 |
| `strategy.py` | 방어형 고객, 고객 구성 최적화 |
| `naver_datalab.py`, `kosis.py` | 외부 API 수집 |
| `medallion.py`, `pipeline.py` | 층별 저장, 숫자 확인, 전체 실행 |
| `synthetic.py` | 원본과 형식이 같은 합성 데이터 |

- **함수 하나는 일 하나만 합니다.** 예를 들어 `clean_card_spending()`은 정제만 하고, 집계는 `build_age_spending_structure()`가 합니다. 그래서 함수마다 따로 테스트할 수 있습니다.
- **이름만 보고 역할을 알 수 있게 했습니다.** `df2`, `tmp` 같은 이름 대신 `build_region_industry_profile`처럼 무엇을 만드는지 적었습니다.
- **주석에는 '무엇'보다 '왜'를 적었습니다.** 예: `load_seoul_future_population()`에 pandas 대신 csv 모듈을 쓰는 이유(닫히지 않은 따옴표)를 적어 두었습니다.
- **노트북의 셀과 새 함수의 대응표**를 [리팩토링 노트 3절](../refactoring_notes.md)에 남겼습니다. 옛 노트북을 보다가 "이 셀은 지금 어디 있지?"를 바로 찾을 수 있습니다.
- **손으로 입력하던 결과표는 모두 데이터에서 계산**하게 바꿨습니다.

## 써 보고 확인한 것

- 원본 데이터로 돌렸을 때 발표 결과 CSV 6개가 **모두 그대로** 나왔습니다 (`pipeline --compare`, 6/6 일치). 구조를 크게 바꿨지만 결과는 바뀌지 않았다는 근거입니다.
- 손으로 입력했던 숫자(서울 14건 vs 100건, p = 0.0206 / 0.0008 / 0.0006, 일치율 95.1% / 90.2% / 90.0%)가 **실제 계산 결과와 같다는 것**도 이 과정에서 확인됐습니다.
- 정리하다가 노트북에서는 안 보이던 문제를 찾았습니다. 서울 장래인구의 90세 이상 누락, 지역 기준 '상위 25%'가 두 종류로 쓰인 점, SLSQP 결과를 버리던 문제 등 11가지를 [리팩토링 노트 4절](../refactoring_notes.md)에 정리했습니다.

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| 노트북을 그대로 두고 정리만 | 실행 순서 의존 문제가 남고, 테스트를 붙이기 어렵습니다 |
| 큰 스크립트 파일 하나 | 함수가 수백 개 섞여 어디를 고쳐야 하는지 찾기 어렵습니다 |
| 클래스 위주 설계 | 분석 단계는 '표를 받아 표를 돌려주는' 일이 대부분이라 함수가 더 단순합니다. API처럼 상태(세션, 인증키)가 있는 곳에만 클래스를 썼습니다 |

## 스스로 점검할 질문

<details><summary>Q1. 노트북에서 패키지로 옮겨서 가장 크게 좋아진 점은?</summary>

실행 순서와 상관없이 같은 결과가 나오고, 함수마다 테스트를 붙일 수 있게 된 점입니다. 그 덕분에 구조를 크게 바꿨는데도 발표 결과 6/6이 그대로인지 명령 한 줄로 확인할 수 있습니다.
</details>

<details><summary>Q2. config.py에 기준값을 모으면 무엇이 좋은가?</summary>

기준을 바꿀 때 한 곳만 고치면 되고, 빠뜨려서 일부 계산만 옛 기준으로 도는 일이 없습니다. 민감도 분석(상위 20 · 25 · 30%)도 같은 값을 가져다 씁니다.
</details>

<details><summary>Q3. 어떤 곳에 클래스를 쓰고 어떤 곳에 함수를 썼나? 왜?</summary>

API 클라이언트(`NaverDataLabClient`, `KosisClient`)만 클래스입니다. 세션, 인증키, 재시도 설정 같은 상태를 들고 여러 번 호출하기 때문입니다. 분석 단계는 입력 표 → 출력 표인 함수로 두어 테스트를 단순하게 했습니다.
</details>
