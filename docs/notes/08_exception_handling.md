# 08. 예외 처리

## 한 줄 요약

오류를 "사용자가 고칠 수 있는 것 / 기다리면 풀리는 것 / 멈춰야 하는 것"으로 나누고, 종류마다 다르게 처리합니다. 공통 원칙은 **조용히 넘어가지 않기**와 **무엇을 하면 되는지 알려 주기**입니다.

## 왜 필요했나

- 노트북에서는 오류가 나면 긴 traceback만 남았습니다. 원본 파일이 빠졌을 때도 첫 번째 빠진 파일에서 멈춰서, 고치고 다시 돌리고 다시 멈추기를 반복했습니다.
- API 호출 제한(429)이나 일시적인 서버 오류에도 그대로 멈췄습니다.
- 반대로 조용히 넘어가는 곳도 있었습니다. 최적화가 답을 찾고도 `success=False`면 결과를 버렸고, 행이 사라져도 아무 경고가 없었습니다.

## 오류 종류와 처리

| 종류 | 예 | 처리 | 코드 |
|---|---|---|---|
| 시작 전에 알 수 있는 것 | 원본 파일이 빠짐 | 시작하자마자 **빠진 파일을 한 번에 모두** 알려 주고 멈춤 | `medallion.check_raw_files()` → `FileNotFoundError` |
| 설정이 없는 것 | 인증키 없음 | 무엇을 어디에 넣으면 되는지 안내. 파일이 없는지 · 줄이 없는지 · 값이 비었는지 구분 | `kosis.read_api_key()`, `NaverDataLabClient.__init__` → `ValueError` |
| 기다리면 풀리는 것 | 연결 끊김, 타임아웃, HTTP 429 · 5xx, KOSIS 서버 오류 | 점점 길게 기다리며 다시 시도 (09 참고) | `KosisClient._get()`, `NaverDataLabClient._post()` |
| 다시 해도 같은 것 | 인증키 만료, 잘못된 요청, 호출 한도 초과 | 다시 시도하지 않고 바로 멈춤. 서버가 보낸 메시지를 그대로 보여 줌 | `KosisApiError` |
| 데이터가 틀린 것 | 층 사이 행 수 · 금액 불일치 | 결과를 내보내지 않고 멈춤 | `DataQualityError` (04 참고) |
| 데이터가 아쉬운 것 | 장래인구 매칭 누락 | 경고로 기록하고 계속 | `check_row(blocking=False)` |
| 라이브러리 판단이 보수적인 것 | SLSQP가 답을 찾고도 `success=False` | `success`를 믿지 않고 **제약을 직접 확인**해서 만족하면 사용 | `strategy.optimize_mix_for_min_change()` |
| 저장소가 안 떠 있는 것 | Docker를 켜지 않고 `--object-store` 실행 | "`docker compose up -d`로 띄운 뒤 다시 실행" 한 줄 안내 | `object_store.main()` → `EndpointConnectionError` |
| 받은 파일이 영수증과 다른 것 | 버킷의 파일이 바뀌었거나 덮어써짐 | 그 파일 이름을 모두 적어 멈춤 | `download_bronze()` → `DataQualityError` |
| '없음'이 정상인 것 | 처음 올리는 객체 · 아직 없는 버킷 (S3 404) | 오류가 아니라 '새로 만들기'로 처리. 다른 S3 오류는 그대로 올림 | `object_store.is_not_found()` |
| 인코딩이 다른 것 | utf-8로 못 읽는 CSV | 다음 후보(cp949)로 다시 시도. 모두 실패하면 마지막 오류를 그대로 올림 | `io_utils.read_csv_with_encoding_fallback()` |

## 지킨 원칙

1. **사용자 정의 예외로 종류를 드러냅니다.** `DataQualityError`, `KosisApiError`는 이름만 봐도 무엇이 문제인지 압니다. 부르는 쪽에서 종류별로 다르게 잡을 수도 있습니다.
2. **예외를 넓게 잡지 않습니다.** `except Exception:`으로 다 삼키지 않고, 처리할 줄 아는 예외(`UnicodeDecodeError`, `requests.ConnectionError` 등)만 잡습니다. 모르는 오류는 그대로 올라가야 원인을 찾을 수 있습니다.
3. **CLI에서는 긴 traceback 대신 한 줄 안내를 보여 줍니다.** `kosis.main()`은 사용자가 고칠 수 있는 오류(인증키 없음, 받은 파일 없음, KOSIS 오류)만 잡아 `[중단] ...` 한 줄로 끝냅니다. 그 밖의 오류는 traceback을 그대로 남깁니다.
4. **오류 메시지에 비밀값이 섞이지 않게 합니다.** requests의 연결 오류 메시지에는 요청 주소 전체가 들어가는데, 그 주소에 KOSIS 인증키가 있습니다. 원래 예외를 그대로 올리지 않고(`from None`) 오류 종류만 담은 예외로 바꿔 올립니다.
5. **멈출 때는 근거를 남깁니다.** `DataQualityError` 메시지에는 실패한 검사 표가 그대로 들어가고, 대사 결과는 파일로도 저장됩니다.

## 써 보고 확인한 것

- 원본이 하나도 없는 폴더로 실행하면 8종 중 빠진 것을 한 줄에 모두 알려 줍니다 (`test_missing_raw_files_are_reported_at_once`).
- 연결 끊김 → 503 → 성공 순서의 응답에서 결과를 받아 오고, 인증키 만료 응답에서는 한 번만 요청하고 멈추는 것을 테스트로 확인했습니다 (`test_kosis.py`).
- 실제로 KOSIS 인증키가 비어 있는 `.env`를 지정했을 때 "줄은 있지만 값이 비어 있습니다"라고 정확히 알려 줘서, 키 값을 보지 않고도 원인을 알 수 있었습니다.
- SLSQP 결과를 제약으로 판단하게 바꾼 뒤, 노트북에서 버려지던 다변화 재조정 답을 쓸 수 있게 됐습니다.

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| `except Exception: pass` | 오류가 사라져 결과가 틀려도 알 수 없습니다 |
| 모든 오류에 재시도 | 인증키 오류처럼 다시 해도 같은 오류는 시간만 낭비하고, 호출 한도를 더 씁니다 |
| 오류 코드(숫자) 반환 | 부르는 쪽에서 확인을 빠뜨리면 그대로 진행됩니다. 예외는 잡지 않으면 멈추므로 더 안전합니다 |

## 스스로 점검할 질문

<details><summary>Q1. 어떤 오류는 다시 시도하고 어떤 오류는 바로 멈추나? 기준은?</summary>

시간이 지나면 풀릴 수 있는 오류(연결 끊김, 서버 과부하, 순간 호출 제한)는 다시 시도합니다. 요청 내용이나 계정 상태가 원인인 오류(인증키 만료, 잘못된 파라미터, 하루 한도 초과)는 몇 초 뒤에 다시 보내도 같으므로 바로 멈춥니다.
</details>

<details><summary>Q2. 빠진 원본을 "한 번에" 알려 주는 것이 왜 중요한가?</summary>

첫 번째 빠진 파일에서 멈추면, 고치고 다시 돌리고 또 멈추는 일을 빠진 파일 수만큼 반복합니다. 시작 전에 모두 확인하면 한 번에 고칠 수 있습니다. 긴 작업을 돌리다 중간에 멈추는 것도 막습니다.
</details>

<details><summary>Q3. `raise ... from None`은 왜 썼나?</summary>

기본적으로 새 예외를 올리면 원래 예외도 traceback에 함께 출력됩니다. 원래 예외(requests 연결 오류) 메시지에 인증키가 든 URL이 들어 있어서, 연결을 끊어 원래 메시지가 출력되지 않게 했습니다.
</details>

<details><summary>Q4. SLSQP의 success=False를 무시해도 괜찮은 근거는?</summary>

success=False여도 결과가 문제의 조건을 모두 만족하면 쓸 수 있는 답입니다. 합계 100, 목표 Stress 이상, HHI 이하, 범위 안을 허용 오차 1e-6으로 직접 확인하고, 하나라도 어기면 None을 돌려줍니다. 라이브러리의 판단 대신 문제의 조건을 기준으로 삼은 것입니다.
</details>
