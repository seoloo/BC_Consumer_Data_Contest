# 02. 테스트

## 한 줄 요약

pytest로 세 종류의 테스트를 둡니다. 손으로 계산한 값과 비교하는 **단위 테스트**, 합성 원본으로 처음부터 끝까지 돌려 보는 **전체 실행 테스트**, 원본으로 돌려 발표 결과와 맞춰 보는 **결과 재현 확인**입니다.

## 왜 필요했나

- 리팩토링은 "코드는 바꾸되 결과는 그대로"여야 합니다. 그런데 노트북에는 결과가 그대로인지 확인할 방법이 눈으로 보는 것밖에 없었습니다.
- 실제로 노트북 안에는 손으로 입력한 결과표가 있었습니다. 계산을 고쳐도 표가 그대로라서, 틀린 숫자가 맞는 숫자처럼 보일 수 있었습니다.
- 원본 데이터는 공개할 수 없어서, 원본이 없는 환경(다른 PC, 나중의 CI)에서도 돌아가는 테스트가 필요했습니다.

## 어떻게 했나

| 종류 | 파일 | 확인하는 것 |
|---|---|---|
| 단위 테스트 | `test_standardization.py`, `test_card_spending_and_stress.py`, `test_diagnosis_and_validation.py`, `test_robustness_and_strategy.py` | 몇 줄짜리 작은 데이터로 손계산한 값과 같은지. 예: 연령 비중, HHI, Stress 공식, 엄격 성장 3조건, 4유형 표 |
| API 테스트 | `test_naver_datalab.py`, `test_kosis.py` | 실제 서버 대신 가짜 응답으로 파싱 · 재시도 · 저장 동작 |
| 전체 실행 테스트 | `test_pipeline_smoke.py` | 합성 원본으로 Bronze → Silver → Gold → 대사 → 내보내기가 끊기지 않는지, 결과 열 이름이 발표 CSV와 같은지 |
| 합성 데이터 테스트 | `test_synthetic.py` | 같은 시드 → 같은 파일, 원본의 까다로운 형식이 들어 있는지 |
| 결과 재현 확인 | `python -m future_stress.pipeline --compare` | 원본으로 돌린 결과가 `results/`의 발표 CSV와 같은지 (원본이 있는 PC에서만) |

- **작은 데이터를 일부러 만듭니다** (`tests/conftest.py`). 예를 들어 "성동구 · 서양음식은 매달 늘어남", "도봉구는 4월 결제가 없음", "성별 코드 9인 행은 빠져야 함"처럼 확인할 상황을 하나씩 넣습니다.
- **검사가 실제로 잡아내는지도 확인합니다.** `test_quality_check_detects_lost_rows`는 Silver에서 일부러 한 행을 지우고 대사가 '실패'를 내는지 봅니다. 통과만 확인하면 아무것도 안 하는 검사도 통과하기 때문입니다.
- **무거운 준비는 한 번만 합니다.** 합성 원본 생성(약 10초)은 `scope="session"` fixture로 한 번만 만들고 여러 테스트가 같이 씁니다.
- 모든 계층은 pytest가 만든 임시 폴더(`tmp_path`)에 만들어서 실제 `data/` 폴더를 건드리지 않습니다.

## 써 보고 확인한 것

- 테스트 **53개**가 약 45초에 모두 통과합니다 (2026-10-21 기준).
- 발표 결과 **6/6 일치**. 손으로 입력했던 Fisher 검정의 14/0 · 74/26을 데이터로 만들어도 p = 0.0206이 나오는지 테스트로 고정했습니다.
- 리팩토링하면서 SLSQP 최적화가 답을 찾고도 `success=False`를 돌려주는 경우를 발견했습니다. 노트북은 이 답을 버리고 있었고, 지금은 제약을 직접 확인해서 받아들입니다 (`strategy.py`).
- 합성 데이터 전체 실행 테스트 덕분에, 원본 없이도 파일 읽기부터 결과 저장까지 연결이 깨지지 않았는지 매번 확인됩니다.

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| unittest (표준 라이브러리) | 테스트마다 클래스를 만들어야 해서 길어집니다. pytest는 `assert` 한 줄로 되고 fixture가 편합니다 |
| 원본으로만 확인 | 원본이 없는 곳에서는 아무것도 확인할 수 없습니다 |
| 실제 API로 테스트 | 인증키가 필요하고, 서버 상태나 호출 한도에 따라 테스트 결과가 바뀝니다 |

## 스스로 점검할 질문

<details><summary>Q1. 단위 테스트와 전체 실행(smoke) 테스트는 각각 무엇을 잡나?</summary>

단위 테스트는 계산 하나하나가 맞는지(공식, 기준)를 잡습니다. 전체 실행 테스트는 계산은 맞아도 단계 사이 연결(파일 이름, 열 이름, 저장 · 읽기)이 깨진 경우를 잡습니다.
</details>

<details><summary>Q2. "검사가 실패를 내는지" 테스트하는 이유는?</summary>

검사 코드에 버그가 있어 항상 '통과'를 내도, 통과만 확인하는 테스트는 같이 통과합니다. 일부러 잘못된 데이터를 넣고 '실패'가 나오는지 봐야 검사가 실제로 동작한다는 것을 알 수 있습니다.
</details>

<details><summary>Q3. 외부 API를 테스트할 때 실제 서버를 부르지 않는 이유는?</summary>

인증키 없이도 돌아가야 하고, 서버 장애나 호출 한도 때문에 테스트 결과가 바뀌면 안 되기 때문입니다. 대신 서버 응답 모양을 흉내 낸 가짜 세션으로 재시도 · 오류 처리 · 저장을 확인합니다. 실제 서버와 맞는지는 별도로 한 번 확인합니다.
</details>
