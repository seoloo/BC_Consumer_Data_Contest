# 16. dbt (SQL 모델 · 테스트)

## 한 줄 요약

파이썬 함수로 하던 Silver 규칙(개인 결제만 남기기, 코드 → 이름, 5세 구간 고르기, 증감률)과 Gold 계산(연령별 소비구조, 성장 지표, Future Stress, 4유형)을 **dbt SQL 모델**로 옮겼습니다. 기준표는 seed(CSV)로, 숫자 확인은 dbt tests로 두었고, 결과는 파이썬과 같습니다(Gold 합계 두 종류만 소수 15째 자리 차이). 통계 검정 · 최적화 · 보정 검증은 SQL에 없는 계산이라 파이썬에 남겼습니다.

## 결정 기록

| 날짜 | 결정 | 이유 |
|---|---|---|
| 2026-10-21 | dbt를 Docker 공식 이미지로 실행 | dbt가 Python 3.14를 아직 지원하지 않을 수 있음. PC에 Python을 더 설치하지 않고 버전 고정 (`ghcr.io/dbt-labs/dbt-postgres:1.9.0`) |
| 2026-10-21 | compose에서 `profiles: ["tools"]` | dbt는 계속 떠 있는 서버가 아니라 한 번 돌고 끝나는 명령이라, `up`으로는 안 뜨고 `docker compose run --rm dbt ...`로만 실행 |
| 2026-10-21 | 코드 → 이름 규칙은 seed(CSV) | 규칙이 SQL 안 `CASE` 문에 숨지 않고 표로 보이게. 파이썬 `age_groups.py`의 딕셔너리와 같은 내용 |
| 2026-10-21 | 외부 패키지(dbt_utils) 안 씀 | 필요한 것은 '여러 열 조합이 겹치지 않는지' 테스트 하나. 패키지를 쓰면 실행 전에 인터넷에서 받는 단계(`dbt deps`)가 생김 → 일반 테스트를 직접 만듦 |
| 2026-10-21 | 서울 90세 이상 누락을 그대로 재현 | 이번 목표는 '옮겨도 결과가 같다'. 고치면 파이썬 결과와 달라져 비교할 수 없음. seed 설명에 재현용이라고 표시 |
| 2026-10-21 | Gold도 dbt로 (3-3) | Silver만 옮기면 계산 규칙이 파이썬과 SQL 두 곳에 나뉨. Gold까지 옮겨 SQL만으로 결과를 다시 만들 수 있는지 확인 |
| 2026-10-21 | 반올림은 '실수로 계산 + 짝수 쪽' 매크로 | 파이썬(numpy)은 12.25 → 12.2, PostgreSQL `round(numeric)`은 12.3. 비중 · 증감률을 반올림한 값으로 다음 계산을 하므로 한 칸이 판정을 바꿀 수 있음. `round(float8)`이 짝수 쪽인 것을 직접 확인(2.5 → 2) |
| 2026-10-21 | 핵심 연령대 동점은 `collate "C"` 순서로 | 파이썬 `idxmax`는 '먼저 나온 행'을 고르고, 그 순서는 문자 코드 순. DB 기본 정렬(언어 규칙)과 다를 수 있음 |
| 2026-10-21 | 4유형 건수는 항상 4줄 (파이썬도 고침) | 합성 데이터에 지속성장형이 없자 파이썬은 줄을 빼고 dbt는 0으로 보여 줘 비교가 어긋남. '0건'도 결과라서 dbt 쪽에 맞춤 |
| 2026-10-21 | 작업은 main에 바로 커밋 | 혼자 작업하고 바로 합쳐서 브랜치가 역할을 못 함 (12 참고) |

## 왜 필요했나

- 파이썬 Silver는 결과가 맞아도, 규칙(어떤 코드를 빼는지, 어떤 행을 고르는지)이 함수 안에 있어 코드를 열어 봐야 알 수 있습니다.
- 표가 많아지면 "이 표는 어디서 왔고, 무엇을 검사하나"를 따라가기 어렵습니다. dbt는 모델 사이의 관계(lineage)를 알아서 순서대로 만들고, 표마다 테스트를 붙입니다.
- 데이터베이스 안에서 SQL로 만들어 두면 대시보드, 다른 사람의 SQL 조회가 같은 결과를 씁니다.

## 어떻게 했나

```text
dbt/
  dbt_project.yml          층 → 스키마 (seed → ref, silver 모델 → silver), 기준연도 같은 변수
  profiles.yml             접속 정보. 비밀번호는 docker compose가 넘기는 환경변수(.env)에서
  models/sources.yml       raw 스키마 표 (파이썬이 넣음, dbt는 읽기만) + 원본 테스트
  models/silver/*.sql      Silver 모델 2개
  models/silver/schema.yml 모델 설명 + 테스트
  models/gold/*.sql        Gold 모델 9개 (+ 표로 저장하지 않는 중간 단계 1개)
  seeds/*.csv              기준표 4개 (연령대, BC 연령 코드, BC 성별 코드, 서울 5세 구간 목록)
  macros/                  연령 표기 → 연령대, 스키마 이름 규칙, 여러 열 조합 중복 테스트,
                           파이썬과 같은 반올림, Gold 공통 계산(소비구조 · 프로필 · 시 단위로 합치기)
  tests/                   대사 테스트 (raw = Silver + 뺀 결제, 집계 전후 금액, 비중 합 ≈ 100)
```

| 모델 | 하는 일 | 파이썬에서는 |
|---|---|---|
| `silver.silver_card_spending` | 성별 · 연령 코드를 기준표와 join → 기준표에 없는 코드(3 · x)는 저절로 빠짐, 이름으로 바꾸고 업종명 공백 제거 | `clean_card_spending()` |
| `silver.silver_future_population` | 서울(CSV)과 부산 · 경기(엑셀)의 서로 다른 고르는 조건 → 하나로 합쳐 연령대별 합계 → 2026년 대비 증감률 | `load_seoul_future_population()`, `load_kosis_future_population()` |

| `gold_gyeonggi_city_age_spending_structure` | 경기 일반구를 시로 합친 뒤 같은 계산 | `merge_gyeonggi_districts_into_cities()` + 같은 함수 |

**dbt 테스트 (Silver 25개 → Gold까지 41개)**

| 종류 | 예 | 확인하는 것 |
|---|---|---|
| `not_null` | `silver_card_spending.amount` | 빈 값 없음 |
| `unique` | 기준표의 코드 | 같은 코드가 두 번 없음 (join에서 행이 늘어나지 않게) |
| `accepted_values` | 성별은 남성 · 여성, raw 시도는 3개 | 정해 둔 값만 |
| `relationships` | Silver 연령대 → `ref.age_groups` | 기준표에 없는 연령대가 없음 (예전 '20대미만' 문제) |
| `unique_combination` (직접 만듦) | 장래인구의 시도 × 시군구 × 연령대 | 한 줄씩만 → Gold에서 결제와 붙일 때 두 번 세지 않음 |
| 대사 (직접 만듦) | `assert_card_silver_reconciles_with_raw` | raw 결제 = Silver 결제 + 뺀 결제 (행 수 · 금액) |
| 대사 (직접 만듦) | `assert_gold_amount_reconciles_with_silver` | 집계 전후 금액이 같음 (전국 · 경기 시 단위) = 파이썬 대사 5 · 6번 |
| 직접 만듦 | `assert_amount_share_sums_to_100` | 지역 × 업종마다 비중 합이 100 ± 0.3 (반올림 오차 범위) |
| `not_null` (경고) | `gold_age_stress.change_rate_2040` | 장래인구 매칭 누락 = 파이썬 대사 7 ~ 9번 '경고'와 같음. 멈추지 않고 알리기만 |

**스키마 이름 규칙:** dbt는 기본으로 `public_silver`처럼 이름을 붙입니다. 층 이름이 곧 스키마 이름이 되도록 바꿨고, 합성 데이터(`--target synthetic`)는 `synthetic_silver`처럼 앞에 붙여 원본 결과와 섞이지 않게 했습니다.

## 써 보고 확인한 것

| 확인 | 원본 | 합성 |
|---|---|---|
| `dbt build` (seed 4 · 모델 2 · 테스트 25) | 31개 모두 통과, 2.6초 | 31개 모두 통과 |
| `silver_card_spending` | 159,235행 | 113,496행 |
| `silver_future_population` | 432행 | 432행 |
| **파이썬 Silver와 비교** (`warehouse compare-silver`) | **318,470칸 + 3,024칸 모두 같음** | 226,992칸 + 3,024칸 모두 같음 |

**Gold (3-3, 원본 데이터)**

| 확인 | 결과 |
|---|---|
| `dbt build` (seed 5 · 모델 11 · 테스트 41) | 57개 모두 통과, 경고 0 |
| Gold 7개 표 비교 (`warehouse compare-gold`) | **125,805칸, 다른 칸 0 · 한쪽에만 0** |
| 마지막 자리까지 같은 칸 | 반올림한 값(비중 · 증감률 · 성장 지표 · 연령대별 기여도 · 유형)은 모두. 합계 두 종류만 아주 작게 다름: 연령 집중도 최대 1.1×10⁻¹⁶, 지역 × 업종 Stress 최대 3.6×10⁻¹⁵ |
| 서울 발표 기준 | 114건 → **성장 14 · 비성장 100** (발표와 같음) |
| 4유형 건수 | 서울 9 · 0 · 41 · 11 / 부산 4 · 0 · 34 · 3 / 경기 4 · 9 · 17 · 44 (착시 · 지속 · 구조취약 · 회복기회, 파이썬과 같음) |
| 합성 데이터 | 57개 통과, 7개 표 모두 같음 (4유형 건수 표를 고친 뒤) |

- **합계가 15째 자리에서 다른 이유:** pandas의 그룹 합계는 반올림 오차를 줄이는 보정 덧셈(Kahan)을 쓰고, PostgreSQL은 그냥 더합니다. 실수는 더하는 방법에 따라 마지막 자리가 달라질 수 있습니다. 발표 결과는 소수 둘째 자리로 반올림하고 4유형 판정(0보다 크냐 작냐)도 모두 같아서 결과에는 영향이 없습니다. 그래서 비교 허용 오차를 0.000001로 두었습니다.
- **반올림을 맞추지 않았다면 틀렸을 수 있습니다.** 비중을 반올림한 값으로 Stress를 계산하고, 월평균 증감률을 반올림한 뒤 0과 비교해 성장을 판정합니다(0.04%는 0.0이 되어 '성장 아님'). 반올림 한 칸이 판정을 바꿀 수 있어서, Gold 전에 Silver까지 같은 방식으로 바꿔 두었습니다.
- **반올림 방식 걱정은 실제로는 문제가 없었습니다.** 파이썬(pandas)의 `round`는 정확히 .5일 때 짝수 쪽으로, PostgreSQL의 `round`는 0에서 먼 쪽으로 반올림합니다. 증감률이 다를 수 있어 비교했는데, 432줄 × 3개 연도 모두 같았습니다. 정확히 .x5에 걸리는 값이 없었기 때문입니다. Gold로 넘어가면서 다시 확인할 부분으로 남깁니다.
- 처음 실행에서 31개가 모두 통과했습니다. 파이썬 규칙을 리팩토링 때 함수 하나씩 정리해 둔 덕분에 SQL로 옮길 때 빠뜨린 조건이 없었습니다.
- **커밋에서 seed CSV가 빠질 뻔했습니다.** 원본 보호를 위해 `.gitignore`가 모든 `*.csv`를 제외하고 있어서, 기준표 CSV 4개도 함께 제외됐습니다. 커밋 목록을 보고 알아채서 `!dbt/seeds/*.csv` 예외를 넣었고, dbt가 실행마다 만드는 개인 식별 파일(`dbt/.user.yml`)은 빼 두었습니다. 원본 CSV와 `output/`이 여전히 제외되는 것도 다시 확인했습니다.
- 성별 · 연령 코드를 `CASE` 대신 기준표 join으로 거르니, "어떤 코드가 빠지는가"를 SQL을 읽지 않고 seed 파일만 봐도 알 수 있습니다.

## 데이터 사전 · ERD 자동 생성 (3-4)

| 날짜 | 결정 | 이유 |
|---|---|---|
| 2026-10-21 | 문서는 손으로 쓰지 않고 DB · dbt 결과에서 자동으로 | 손으로 쓴 표 · 열 문서는 표가 바뀌면 곧 틀려짐 |
| 2026-10-21 | 열 설명은 dbt docs 블록(`models/docs.md`) 한 곳에 | 시도 · 시군구 · 비중 같은 열이 여러 표에 나옴. 같은 설명을 여러 번 쓰면 하나만 고쳐지는 일이 생김 |
| 2026-10-21 | `persist_docs`로 PostgreSQL COMMENT에도 저장 | DB 도구로 표를 열어도 뜻이 보이게. 생성 스크립트도 이 COMMENT를 읽음 |
| 2026-10-21 | ERD의 선 = dbt 연결 테스트 | 그림에 그린 연결이 실제로 매번 검사되는 연결이 되게. 여러 열 연결은 `composite_relationships` 테스트를 직접 만듦 |
| 2026-10-21 | 그림은 Mermaid | GitHub가 마크다운 안에서 바로 그려 줌. 텍스트라 git으로 바뀐 내용이 보임 |

```text
dbt/models/docs.md · schema.yml    설명 (한 곳)
        │ dbt build (persist_docs)
        ▼
PostgreSQL COMMENT · 열 · 행 수 ──┐
dbt/target/manifest.json ─────────┤ python -m future_stress.storage.warehouse_docs
  (계보 = ref/source, 열쇠 = unique 테스트, 연결 = relationships 테스트)
                                  ▼
                     docs/warehouse/README.md (표 18개 · 테스트 49개 · 계보 · ERD · 열 목록)
```

**써 보고 확인한 것**
- 처음 만든 문서는 **테스트 수를 42개로 적었습니다(실제 49개).** 원본(source)에 붙은 테스트와 여러 표를 함께 보는 대사 테스트는 어느 표에 붙었는지(`attached_node`)가 비어 있어 빠졌습니다. dbt 실행 결과(seed 5 + 모델 11 + 테스트 49 = 65단계)와 맞춰 보고 찾았습니다.
- **ERD의 연결 기호가 처음엔 틀렸습니다.** 부모 표의 열쇠 전체로 연결될 때만 '정확히 하나'(`||`)여야 하는데, 자식 열 이름(`main_age_group`)과 부모 열 이름(`age_group`)이 다른 경우를 '하나 이상'으로 그렸습니다. 부모 쪽 열 이름으로 비교하도록 고쳤고, 테스트로 고정했습니다.
- Mermaid 문법이 맞는지는 Mermaid 11로 두 그림을 실제로 그려 확인했습니다 (오류 없이 2개).
- 여러 열 연결 테스트 5개를 새로 넣어 dbt 테스트가 41개 → 49개(Gold 기준 경고 1 포함)가 됐고 모두 통과합니다.

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| 파이썬 함수 그대로 | 규칙과 검사가 코드 안에 있어 보기 어렵고, DB를 쓰는 다른 도구와 결과를 함께 쓰기 어렵습니다 |
| 데이터 사전을 손으로 작성 | 표가 바뀌면 문서가 틀려집니다. 설명은 한 곳에 쓰고 문서는 자동으로 만듭니다 |
| `dbt docs serve` 웹 화면만 | 띄워야 볼 수 있고 GitHub에서 바로 안 보입니다. 마크다운 + Mermaid는 저장소에서 바로 보입니다 |
| SQL 파일을 직접 순서대로 실행 | 표 사이 순서 · 테스트 · 문서를 직접 관리해야 합니다. dbt는 `ref()`로 순서를 알아서 정합니다 |
| 저장 프로시저 | DB 안에 숨어 git으로 바뀐 내용을 보기 어렵습니다 |
| dbt를 PC에 설치 | Python 3.14 지원이 불확실하고, PC마다 버전이 달라질 수 있습니다 |
| dbt_utils 같은 패키지 | 지금 필요한 테스트는 하나라 직접 만드는 편이 단순합니다 |

## 스스로 점검할 질문

<details><summary>Q1. dbt의 source, ref, seed는 각각 무엇인가?</summary>

source는 dbt 밖에서 들어온 표(여기서는 파이썬이 넣은 raw)입니다. ref는 dbt가 만든 다른 모델이나 seed를 가리키며, dbt는 ref를 보고 만드는 순서를 정합니다. seed는 저장소의 작은 CSV를 표로 올린 것으로, 여기서는 코드 → 이름 기준표입니다.
</details>

<details><summary>Q2. dbt 테스트는 어떻게 '통과'를 판단하나?</summary>

테스트는 '문제가 되는 행'을 찾는 SELECT 문입니다. 결과가 0행이면 통과입니다. 예를 들어 대사 테스트는 "raw 행 수 ≠ Silver 행 수 + 뺀 행 수"인 경우만 돌려주므로, 숫자가 맞으면 0행입니다.
</details>

<details><summary>Q3. 파이썬 Silver와 비교한 이유는? 무엇을 비교했나?</summary>

규칙을 SQL로 옮기면서 결과가 바뀌지 않았다는 증거가 필요했습니다(리팩토링 때 발표 결과 6/6과 같은 역할). 열쇠 열(시군구, 연령대 등)로 두 표를 맞춘 뒤 값 열(금액, 인구, 증감률)을 한 칸씩 비교했고, 한쪽에만 있는 줄과 행 수도 함께 봤습니다.
</details>

<details><summary>Q4. 파이썬과 SQL의 반올림이 왜 다를 수 있고, 어떻게 맞췄나?</summary>

파이썬(numpy)은 실수로 계산한 뒤 정확히 .5면 짝수 쪽으로 반올림하고(12.25 → 12.2), PostgreSQL의 `round(numeric)`은 0에서 먼 쪽으로 반올림합니다(12.3). 계산을 실수(`double precision`)로 하고 `round(float8)`(짝수 쪽)을 쓰는 매크로를 만들어 맞췄고, 2.5 → 2가 되는 것을 직접 확인했습니다. 반올림한 값으로 다음 계산과 판정을 하므로 한 칸 차이가 결과를 바꿀 수 있습니다.
</details>

<details><summary>Q5. Gold 합계가 소수 15째 자리에서 다른데 '같다'고 할 수 있나?</summary>

실수 덧셈은 순서와 방법(보정 덧셈 여부)에 따라 마지막 자리가 달라집니다. 차이가 10⁻¹⁵ 수준이고, 결과는 소수 둘째 자리로 반올림하며, 유형 판정이 모두 같으므로 '결과가 같다'고 봅니다. 대신 '완전히 같은 칸'과 '아주 작게 다른 칸'을 나눠 세어, 어떤 표의 어떤 열이 얼마나 다른지 기록했습니다.
</details>

<details><summary>Q6. 데이터 사전을 자동으로 만들면 무엇이 좋은가? 이 프로젝트에서 어떻게 했나?</summary>

손으로 쓴 문서는 표가 바뀌는 순간 틀려지고, 틀린 문서는 없는 문서보다 해롭습니다. 설명은 dbt schema.yml · docs 블록 한 곳에만 쓰고(PostgreSQL COMMENT에도 저장), 스크립트가 실제 DB의 열 · 행 수와 dbt manifest의 계보 · 테스트를 읽어 문서를 다시 만듭니다. ERD의 선도 연결 테스트에서 뽑으니, 그림에 있는 연결은 모두 매번 검사되는 연결입니다.
</details>

<details><summary>Q7. 서울 90세 이상 누락처럼 알려진 문제를 왜 SQL에서도 그대로 두었나?</summary>

이번 단계의 목표는 '같은 결과'를 SQL로 내는 것이라, 문제를 고치면 비교 기준이 사라집니다. 옮기는 일과 고치는 일을 나눠야 각각이 맞는지 확인할 수 있습니다. 대신 seed 설명에 재현용이라고 적어 두었고, 고치는 일은 따로 진행할 예정입니다.
</details>
