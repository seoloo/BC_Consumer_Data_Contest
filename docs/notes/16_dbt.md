# 16. dbt (SQL 모델 · 테스트)

## 한 줄 요약

파이썬 함수로 하던 Silver 규칙(개인 결제만 남기기, 코드 → 이름, 5세 구간 고르기, 증감률)을 **dbt SQL 모델**로 옮겼습니다. 기준표는 seed(CSV)로, 숫자 확인은 dbt tests로 두었고, 결과는 파이썬 Silver와 한 칸도 다르지 않습니다.

## 결정 기록

| 날짜 | 결정 | 이유 · 사용자 말 |
|---|---|---|

| 2026-10-21 | 코드 → 이름 규칙은 seed(CSV) | 규칙이 SQL 안 `CASE` 문에 숨지 않고 표로 보이게. 파이썬 `age_groups.py`의 딕셔너리와 같은 내용 |

| 2026-10-21 | 작업은 main에 바로 커밋 | 사용자 "굳이 브랜치를 나눠서 할 필요 있을까?" → 혼자 작업하고 바로 합쳐서 브랜치가 역할을 못 함 (12 참고) |

## 왜 필요했나

- 파이썬 Silver는 결과가 맞아도, 규칙(어떤 코드를 빼는지, 어떤 행을 고르는지)이 함수 안에 있어 코드를 열어 봐야 알 수 있습니다.
- 표가 많아지면 "이 표는 어디서 왔고, 무엇을 검사하나"를 따라가기 어렵습니다. dbt는 모델 사이의 관계(lineage)를 알아서 순서대로 만들고, 표마다 테스트를 붙입니다.
- 데이터베이스 안에서 SQL로 만들어 두면 대시보드, 다른 사람의 SQL 조회가 같은 결과를 씁니다.

## 어떻게 했나

```text
dbt/
  dbt_project.yml          층 → 스키마 (seed → ref, silver 모델 → silver), 기준연도 같은 변수
  profiles.yml             접속 정보. 비밀번호는 docker compose가 넘기는 환경변수(.env)에서
  models/sources.yml       raw 스키마 표 (파이썬이 넣음, dbt는 읽기만) + 원본 테스트
  models/silver/*.sql      Silver 모델 2개
  models/silver/schema.yml 모델 설명 + 테스트
  seeds/*.csv              기준표 4개 (연령대, BC 연령 코드, BC 성별 코드, 서울 5세 구간 목록)
  macros/                  연령 표기 → 연령대, 스키마 이름 규칙, 여러 열 조합 중복 테스트
  tests/                   대사 테스트 (raw = Silver + 뺀 결제)
```

| 모델 | 하는 일 | 파이썬에서는 |
|---|---|---|
| `silver.silver_card_spending` | 성별 · 연령 코드를 기준표와 join → 기준표에 없는 코드(3 · x)는 저절로 빠짐, 이름으로 바꾸고 업종명 공백 제거 | `clean_card_spending()` |
| `silver.silver_future_population` | 서울(CSV)과 부산 · 경기(엑셀)의 서로 다른 고르는 조건 → 하나로 합쳐 연령대별 합계 → 2026년 대비 증감률 | `load_seoul_future_population()`, `load_kosis_future_population()` |

**dbt 테스트 25개**

| 종류 | 예 | 확인하는 것 |
|---|---|---|
| `not_null` | `silver_card_spending.amount` | 빈 값 없음 |
| `unique` | 기준표의 코드 | 같은 코드가 두 번 없음 (join에서 행이 늘어나지 않게) |
| `accepted_values` | 성별은 남성 · 여성, raw 시도는 3개 | 정해 둔 값만 |
| `relationships` | Silver 연령대 → `ref.age_groups` | 기준표에 없는 연령대가 없음 (예전 '20대미만' 문제) |
| `unique_combination` (직접 만듦) | 장래인구의 시도 × 시군구 × 연령대 | 한 줄씩만 → Gold에서 결제와 붙일 때 두 번 세지 않음 |
| 대사 (직접 만듦) | `assert_card_silver_reconciles_with_raw` | raw 결제 = Silver 결제 + 뺀 결제 (행 수 · 금액) |

**스키마 이름 규칙:** dbt는 기본으로 `public_silver`처럼 이름을 붙입니다. 층 이름이 곧 스키마 이름이 되도록 바꿨고, 합성 데이터(`--target synthetic`)는 `synthetic_silver`처럼 앞에 붙여 원본 결과와 섞이지 않게 했습니다.

## 써 보고 확인한 것

| 확인 | 원본 | 합성 |
|---|---|---|
| `dbt build` (seed 4 · 모델 2 · 테스트 25) | 31개 모두 통과, 2.6초 | 31개 모두 통과 |
| `silver_card_spending` | 159,235행 | 113,496행 |
| `silver_future_population` | 432행 | 432행 |
| **파이썬 Silver와 비교** (`warehouse compare-silver`) | **318,470칸 + 3,024칸 모두 같음** | 226,992칸 + 3,024칸 모두 같음 |

- **반올림 방식 걱정은 실제로는 문제가 없었습니다.** 파이썬(pandas)의 `round`는 정확히 .5일 때 짝수 쪽으로, PostgreSQL의 `round`는 0에서 먼 쪽으로 반올림합니다. 증감률이 다를 수 있어 비교했는데, 432줄 × 3개 연도 모두 같았습니다. 정확히 .x5에 걸리는 값이 없었기 때문입니다. Gold로 넘어가면서 다시 확인할 부분으로 남깁니다.
- 처음 실행에서 31개가 모두 통과했습니다. 파이썬 규칙을 리팩토링 때 함수 하나씩 정리해 둔 덕분에 SQL로 옮길 때 빠뜨린 조건이 없었습니다.
- 성별 · 연령 코드를 `CASE` 대신 기준표 join으로 거르니, "어떤 코드가 빠지는가"를 SQL을 읽지 않고 seed 파일만 봐도 알 수 있습니다.

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| 파이썬 함수 그대로 | 규칙과 검사가 코드 안에 있어 보기 어렵고, DB를 쓰는 다른 도구와 결과를 함께 쓰기 어렵습니다 |
| SQL 파일을 직접 순서대로 실행 | 표 사이 순서 · 테스트 · 문서를 직접 관리해야 합니다. dbt는 `ref()`로 순서를 알아서 정합니다 |
| 저장 프로시저 | DB 안에 숨어 git으로 바뀐 내용을 보기 어렵습니다 |
| dbt를 PC에 설치 | Python 3.14 지원이 불확실하고, PC마다 버전이 달라질 수 있습니다 |
| dbt_utils 같은 패키지 | 지금 필요한 테스트는 하나라 직접 만드는 편이 단순합니다 |

## 스스로 점검할 질문

<details><summary>Q1. dbt의 source, ref, seed는 각각 무엇인가?</summary>

source는 dbt 밖에서 들어온 표(여기서는 파이썬이 넣은 raw)입니다. ref는 dbt가 만든 다른 모델이나 seed를 가리키며, dbt는 ref를 보고 만드는 순서를 정합니다. seed는 저장소의 작은 CSV를 표로 올린 것으로, 여기서는 코드 → 이름 기준표입니다.
</details>

<details><summary>Q2. dbt 테스트는 어떻게 '통과'를 판단하나?</summary>

테스트는 '문제가 되는 행'을 찾는 SELECT 문입니다. 결과가 0행이면 통과입니다. 예를 들어 대사 테스트는 "raw 행 수 ≠ Silver 행 수 + 뺀 행 수"인 경우만 돌려주므로, 숫자가 맞으면 0행입니다.
</details>

<details><summary>Q3. 파이썬 Silver와 비교한 이유는? 무엇을 비교했나?</summary>

규칙을 SQL로 옮기면서 결과가 바뀌지 않았다는 증거가 필요했습니다(리팩토링 때 발표 결과 6/6과 같은 역할). 열쇠 열(시군구, 연령대 등)로 두 표를 맞춘 뒤 값 열(금액, 인구, 증감률)을 한 칸씩 비교했고, 한쪽에만 있는 줄과 행 수도 함께 봤습니다.
</details>

<details><summary>Q4. 서울 90세 이상 누락처럼 알려진 문제를 왜 SQL에서도 그대로 두었나?</summary>

이번 단계의 목표는 '같은 결과'를 SQL로 내는 것이라, 문제를 고치면 비교 기준이 사라집니다. 옮기는 일과 고치는 일을 나눠야 각각이 맞는지 확인할 수 있습니다. 대신 seed 설명에 재현용이라고 적어 두었고, 고치는 일은 따로 진행할 예정입니다.
</details>
