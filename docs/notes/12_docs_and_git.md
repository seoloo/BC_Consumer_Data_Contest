# 12. 문서 자동화 · Git 작업 방식

## 한 줄 요약

흐름도는 HTML로 쓰고 스크립트 한 번으로 PNG를 다시 만듭니다. 작업은 확인(테스트 · 원본 6/6)이 끝나면 main에 바로 커밋하고, 중간에 멈출 수 있는 작업만 브랜치를 씁니다.

## 결정 기록

| 날짜 | 결정 | 이유 · 사용자 말 |
|---|---|---|
| 2026-10-20 | 기능마다 브랜치 + 첫 큰 작업은 PR | main을 항상 돌아가는 상태로 두려고 |
| 2026-10-21 | **main에 바로 커밋**, 멈출 작업만 브랜치 | 사용자 "굳이 브랜치를 나눠서 할 필요 있을까?" — 혼자 작업하고 매번 바로 합쳐서, 합치기 전에 따로 검토한 적이 없었음. 브랜치가 역할을 못 하고 '합칠까요?' 단계와 병합 커밋만 늘었음 |
| (예정) Phase 4 | 브랜치 → PR → 자동 테스트 → 합치기로 다시 | GitHub Actions가 붙으면 PR마다 테스트가 자동으로 돌아 브랜치가 의미를 가짐 |

## 흐름도 자동화

### 왜 필요했나

- 흐름도를 그림 도구로 그리면, 숫자 하나 바뀔 때마다 손으로 다시 그려야 합니다. 그러다 보면 그림과 코드가 서로 다른 말을 하게 됩니다.
- 그림 하나에 다 담으면 너무 길어서 README · 블로그에서 잘 안 보였습니다.

### 어떻게 했나

- 코드: `docs/diagrams/render.py`, 스타일: `docs/diagrams/_style.css`
- 흐름도는 HTML + 공통 CSS로 씁니다. `render.py`가 설치된 Chrome을 화면 없이(headless) 실행해 PNG로 캡처합니다.
- 캡처한 뒤 아래쪽 빈 배경을 자동으로 잘라냅니다. 높이를 넉넉히 적어 두면 내용이 잘리지 않습니다.
- HTML 블록에 `data-part="1"`처럼 번호를 붙이면, 번호별로 나눈 조각 그림(`parts/`)도 함께 만듭니다. 조각마다 'n / 전체' 표시가 붙습니다.

### 써 보고 확인한 것

- 흐름도 10장(00 ~ 09)과 조각 그림을 명령 한 줄로 다시 만듭니다. 로드맵(09)은 작업이 끝날 때마다 고쳐서 v5까지 왔습니다.
- 처음에는 그림 아래쪽이 잘리는 문제가 있었는데, 빈 배경을 잘라내는 방식으로 바꿔 해결했습니다.

## Git 작업 방식

### 어떻게 했나

| 규칙 | 이유 |
|---|---|
| ~~기능마다 브랜치~~ → main에 바로 커밋 (2026-10-21부터) | 혼자 작업하고 바로 합치므로. 외부 조건을 기다리는 작업(예: KOSIS 인증키)만 브랜치 |
| 첫 큰 작업은 PR로 합침 (`seoloo/BC_Consumer_Data_Contest#1`) | 무엇이 바뀌었는지 한곳에서 보고 합치기 |
| 커밋 메시지에 '무엇을 · 왜' | 나중에 `git log`만 보고도 바뀐 이유를 알 수 있게 |
| 합칠 때 `--no-ff` 병합 커밋 | 어떤 커밋들이 한 기능이었는지 기록에 남게 |
| 원본 · 층 데이터 · `.env`는 `.gitignore` | 비공개 데이터와 키가 실수로 올라가지 않게 (10 참고) |
| 커밋 전에 테스트 전체 + 원본 6/6 확인 | 깨진 상태가 main에 들어가지 않게 |

### 한 작업의 순서

```text
1. 계획 설명 → 2. 구현 (이름 · 이유 주석) → 3. 테스트 + 원본 6/6 확인
→ 4. 흐름도 · README · 기록 갱신 → 5. main에 커밋 · 푸시
```

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| 그림 도구(Figma, draw.io)로 흐름도 | 숫자가 바뀌면 손으로 다시 그려야 하고, 변경 이력이 git diff로 보이지 않습니다 |
| Mermaid | GitHub에서 바로 보이는 장점이 있지만, 표 · 카드 · 색으로 설명을 많이 담기에는 표현이 제한적입니다 |
| 기능마다 브랜치 (2026-10-21까지 쓰던 방식) | 혼자 작업하고 매번 바로 합치면 검토 단계가 없어 이득이 적고, 병합 커밋과 확인 질문만 늘어납니다. 커밋 전 테스트 · 6/6 확인이 main을 지키는 실제 안전장치입니다 |

## 스스로 점검할 질문

<details><summary>Q1. 흐름도를 코드(HTML)로 관리하면 좋은 점은?</summary>

텍스트라서 git으로 변경 내용을 비교할 수 있고, 숫자나 문구를 고친 뒤 명령 한 줄로 그림을 다시 만들 수 있습니다. 그림과 코드가 어긋나는 일이 줄어듭니다.
</details>

<details><summary>Q2. 브랜치를 언제 쓰고 언제 안 쓰나? 이 프로젝트에서 바꾼 이유는?</summary>

브랜치는 main을 깨끗하게 지키고, 합치기 전에 검토(사람 또는 자동 테스트)할 기회를 줍니다. 혼자 작업하고 매번 바로 합치는 지금은 그 검토 단계가 없어서, 커밋 전에 테스트와 원본 6/6을 확인하는 것으로 충분합니다. 다만 외부 조건을 기다리느라 중간에 멈출 작업은 브랜치에 둡니다. 자동 테스트(GitHub Actions)를 붙이면 PR마다 검사가 돌아서 브랜치를 다시 쓰는 것이 의미 있어집니다.
</details>
