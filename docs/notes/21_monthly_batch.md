# 21. 새 달 원본 처리 (월 배치 보완)

## 한 줄 요약

월 배치 DAG를 만들었지만, 카드 원본 파일 이름과 분석 기간(2026년 1 ~ 6월)이 코드에 고정되어 있어 **새 달 원본이 와도 실제로는 예전 6개월을 다시 처리하는 상태**였습니다. 이를 고쳐 카드 원본을 배치마다 한 파일씩 받아 합치고, 분석 기간을 '데이터의 마지막 달에서 거꾸로 6개월'로 바꿨습니다. 합성 7월 원본으로 파이썬과 dbt가 함께 2 ~ 7월로 옮겨 가는 것을 확인했고, 원본 결과(발표 숫자 6/6)는 그대로입니다.

## 왜 필요했나

- 18번 기록과 `orchestration.py` 설명에 '다음 달 원본이 오면 같은 DAG가 그 달을 처리한다'고 적었습니다. 그런데 실제로는:
  - `RAW_SOURCES["card"]`가 `bc_card_202601_202606.csv` 하나로 고정 → 7월 파일은 Bronze에도 들어가지 않음
  - `has_new_batch`는 7월 파일 이름을 보고 '새 원본 있음'이라고 판단 → 뒤 단계가 예전 6개월을 다시 처리하고 성공으로 끝남
  - 성장 판정 기간(`ANALYSIS_MONTHS`)도 1 ~ 6월로 고정, dbt도 같은 값을 `vars`로 고정
- **실패하지 않고 조용히 틀린 결과를 내는 경우**라 가장 위험합니다. 점검 명령 · 대사 · dbt 테스트 모두 통과했을 것입니다.

## 어떻게 했나

```text
data/raw/bc_card_202601_202606.csv ─┐
data/raw/bc_card_202607_202607.csv ─┼─ load_card_files ─▶ Silver: 2026.01 ~ 07 모두 (같은 달은 늦게 온 파일)
                                    │
                                    └─ 마지막 달 202607 ─▶ 분석 기간 2026.02 ~ 07 (6개월)
                                                              │
                     Gold: 소비구조 · 성장 · Stress · 4유형 ◀──┘ 이 기간의 결제로만
```

| 곳 | 바꾼 것 |
|---|---|
| `card_spending.py` | `load_card_files()` (여러 파일 합치기 · 같은 달은 늦게 온 파일), `analysis_months()` (마지막 달에서 6개월) |
| `config.py` | `ANALYSIS_LENGTH = 6`, `months_ending()`, `MIN_CARD_PAYMENT_COUNT = 11`, `GYEONGGI_FLOW_MONTHS` |
| `medallion.py` | 카드 원본 `bc_card_*.csv`, Gold에서 기간 거르기 + `analysis_window` 표, 대사 '전국 소비구조 금액'을 기간 기준으로, `latest_card_batch()` |
| `warehouse.py` | raw 적재도 같은 합치기 규칙 + `source_file` 열, 여러 파일 지문, 비교 대상에 `analysis_window` |
| `pipeline.py` · `orchestration.py` | 배치 월 = 원본 폴더의 가장 최근 카드 파일 끝월 |
| dbt | `macros/analysis_window.sql` (raw 마지막 달 → 6개월), `int_card_spending_in_window` (기간 거르기), `gold_analysis_window`, 결제 10건 이하 칸 테스트 |
| `synthetic.py` | `--next-month 202607`로 다음 달 원본 하나 만들기, 원본처럼 10건 이하 칸 빼기 |
| 대시보드 | 맨 위에 분석 기간 표시 |

## 써 보고 확인한 것

| 확인 | 결과 |
|---|---|
| 원본 (1 ~ 6월) | 분석 기간 그대로 202601 ~ 202606, **발표 숫자 6/6 일치**, dbt 69단계 통과, dbt = 파이썬 Gold 8개 표 · Silver 2개 표 일치 |
| 합성 6개월 | dbt = 파이썬 일치, 10건 이하 칸 테스트 통과 |
| **합성 + 7월 원본** | Silver 7개월(131,039행), 분석 기간 **202602 ~ 202607** (파이썬 · dbt 같음), Gold 금액 = 2 ~ 7월 Silver 금액(1월 제외), 저장소 `batch_month=202607` 폴더(61개), raw에 파일별 행 수가 남음 (`bc_card_202607_202607.csv` 28,983행) |
| 같은 달 겹침 | 6월이 두 파일에 있으면 늦게 온 파일 값만 (테스트) |
| Airflow (원본) | `dags trigger`로 8단계 모두 한 번씩 성공 |
| 테스트 | 새로 5개 (기간 계산 · 해 넘김 · 겹치는 달 · 합성 다음 달 · 파이프라인 전체), 전체 94개 통과 |

**부딪힌 것**

1. **`airflow dags test`로 확인하다가 한 단계가 '실패'로 기록됐습니다.** 원인은 같은 단계가 두 번 동시에 돈 것이었습니다.
   - `dags test`는 명령을 친 프로세스에서 단계를 직접 돌립니다.
   - 그런데 DAG가 켜져 있어서, 상시로 도는 스케줄러도 같은 실행의 단계를 함께 집어 들었습니다(같은 단계가 다른 프로세스에서 약 2초 먼저 시작).
   - 어제는 DAG를 켜기 전에 써서 드러나지 않았습니다.
   - 켜져 있는 DAG는 `dags trigger`(스케줄러가 돌림)로 실행하도록 README · 운영 매뉴얼을 고쳤습니다.
2. **합성 데이터가 결제 1 ~ 10건 칸도 만들고 있었습니다.** 원본에는 없는 칸이라 새 검사에 걸렸고, 합성 생성기도 원본처럼 빼도록 맞췄습니다.
3. **Bronze는 쌓기만 합니다.** 원본 폴더에서 파일을 지워도 Bronze 복사본은 남습니다. 도착한 원본을 지우지 않는다는 Bronze의 원칙대로라, 시험 뒤에는 합성 폴더를 통째로 지우고 다시 만들었습니다.

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| 분석 기간을 매달 손으로 고치기 (`config` · `dbt vars`) | 잊으면 조용히 틀린 결과가 나오고, 파이썬과 dbt를 따로 고쳐야 합니다 |
| 1월부터 계속 늘어나는 기간 (누적) | '현재 성장'은 최근 6개월로 판단하는 방법입니다. 기간이 늘면 오래된 달이 판단을 끌어당깁니다 |
| raw를 달 단위로 지우고 넣기 (부분 교체) | 더 실제에 가깝지만, 지금 크기(24만 행)는 전체를 다시 넣어도 몇 초입니다. 트랜잭션 안에서 통째로 바꾸는 쪽이 단순하고 되돌리기도 확실합니다. 데이터가 커지면 바꿀 후보 |
| dbt incremental 모델 | 같은 이유. 지금은 매번 전체를 다시 계산해도 20초 안쪽이고, 기간이 옮겨 가면 앞 달의 결과가 바뀌므로 증분보다 전체 재계산이 맞습니다 |

## 스스로 점검할 질문

<details><summary>Q1. 왜 이 문제가 테스트 · 대사에서 걸리지 않았나?</summary>

모든 검사가 '들어온 데이터 안에서 숫자가 맞는가'를 봤기 때문입니다. 7월 파일이 아예 들어오지 않았으니 남은 6개월 안에서는 숫자가 다 맞았습니다. 그래서 이번에는 '새 달 원본을 넣으면 기간이 옮겨 가는가'를 직접 확인하는 테스트(`tests/test_monthly_batch.py`)를 더했습니다. 검사는 데이터가 '맞는지'뿐 아니라 '빠진 게 없는지'도 봐야 합니다.
</details>

<details><summary>Q2. 같은 달이 두 파일에 있으면 왜 늦게 온 파일만 쓰나?</summary>

두 파일을 그냥 합치면 그 달 금액이 두 번 더해집니다. 제공처가 값을 고쳐 다시 보낸 것이라면 늦게 온 쪽이 맞는 값이고, 고친 달은 통째로 바꾸는 것이 가장 단순하고 다시 돌려도 결과가 같습니다(멱등). 행 단위로 섞으면 어느 행이 고쳐진 것인지 알 수 없습니다.
</details>

<details><summary>Q3. dbt가 분석 기간을 DB에서 읽게 한 이유는?</summary>

파이썬은 Silver의 마지막 달로 기간을 정합니다. dbt에 기간을 손으로 넘기면 둘이 다를 수 있습니다. 그래서 dbt도 raw의 마지막 달을 직접 읽어 같은 규칙으로 계산하고, 두 결과의 `analysis_window`를 비교해 같은 기간인지 먼저 확인합니다.
</details>

<details><summary>Q4. 작은 칸 검사는 왜 dbt 테스트로 두었나?</summary>

원본 제공처가 지키는 기준(10건 이하 제공 안 함)이 우리 쪽 결과 공개의 전제이기 때문입니다. 새 원본에서 이 기준이 깨지면(제공 방식이 바뀌었거나 다른 파일이 섞임) dbt build가 실패해 사람이 확인하게 됩니다. 조용히 넘어가면 화면에 작은 칸이 그대로 보일 수 있습니다.
</details>
