# 15. 데이터 웨어하우스 PostgreSQL (raw 스키마)

## 한 줄 요약

Bronze 원본을 PostgreSQL의 `raw` 스키마에 **표기 그대로** 적재합니다. 파이썬은 '파일을 표로 읽기'만 하고, 개인 결제 거르기 · 코드 바꾸기 같은 규칙은 다음 단계에서 dbt(SQL)가 맡습니다.

## 결정 기록

| 날짜 | 결정 | 이유 |
|---|---|---|
| 2026-10-21 | Phase 3를 PostgreSQL raw 적재(3-1)부터 | dbt가 읽을 원본이 DB에 먼저 있어야 해서 |
| 2026-10-21 | dbt는 Docker 공식 이미지로 (3-2부터) | dbt가 Python 3.14를 아직 지원하지 않을 수 있음. 다른 프로젝트도 dbt만 Python 3.12 가상환경을 따로 둠. Docker면 PC에 Python을 더 설치하지 않고 버전도 고정 (`ghcr.io/dbt-labs/dbt-postgres:1.9.0` 받을 수 있는 것 확인) |
| 2026-10-21 | 파이썬 = 파일 읽기, dbt = 규칙 | 인코딩 · 깨진 따옴표 · 병합 셀은 SQL로 다루기 어렵고, 코드 → 이름 · 거르기 · 집계는 SQL이 잘하고 테스트 붙이기 좋음 |
| 2026-10-21 | 통계 검정 · 최적화는 파이썬에 남김 | Mann-Whitney, SLSQP 같은 계산은 SQL에 없음 |
| 2026-10-21 | raw에는 Stress · 4유형에 필요한 두 원본만 | 카드 결제, 장래인구. 생활 · 유동 · 주민등록 인구는 보정 검증용이라 SQL로 옮길 대상이 아님 |
| 2026-10-21 | 합성 데이터는 `raw_synthetic` 스키마 | 객체 저장소 버킷을 나눈 것과 같은 이유 (같은 표면 덮어씀) |

## 왜 필요했나

- Silver · Gold가 Parquet 파일이라 이 PC의 파이썬에서만 다루기 쉬웠습니다. 대시보드, SQL 조회, dbt 같은 다른 도구가 쓰려면 데이터베이스에 있어야 합니다.
- dbt는 데이터베이스 안의 표를 읽어 SQL 모델을 만드는 도구입니다. 그 출발점(원본 표)이 먼저 있어야 합니다.

## 어떻게 했나

| 무엇 | 어디 | 핵심 |
|---|---|---|
| PostgreSQL 띄우기 | `docker-compose.yml`의 `warehouse` | `postgres:16.4`(이미 이 PC에 있던 버전), `127.0.0.1:55532`, 볼륨 `warehouse-data`, `pg_isready` healthcheck |
| 계정 | `local_env.py` | S3 키와 함께 이 PC 전용 DB 비밀번호를 `.env`에 만듦 (기존 `object_store init-env`도 같은 함수를 부름) |
| 파일 → 표 | `warehouse.card_spending_frame()`, `future_population_frame()` | 값 · 표기는 그대로. 카드 CSV는 모두 문자로 읽고 숫자 열만 바꿈. 장래인구는 연도 열만 세로로 풀고, 엑셀 병합 셀은 엑셀에 보이는 그대로 채움 |
| 적재 | `Warehouse.load()` | 원본 지문 · 행 수 · 합계가 지난 적재와 같으면 '변경 없음'. 다르면 한 트랜잭션에서 지우고 → 만들고 → COPY → 대사 → 기록 |
| 대사 | 같은 함수 | DB의 행 수 · 합계(카드 `amt`, 인구 `population`)가 원본 표와 다르면 `DataQualityError` → 되돌림 |
| 기록 | `raw._load_log` | 적재마다 표 · 원본 지문 · 행 수 · 합계 · 상태 · 시각 |
| 파이프라인 | `pipeline --warehouse` | 실행 중에 함께 적재하고, 대사 보고서에 'raw 적재 대사' 두 줄 추가 |

**raw 표 모양**

| 표 | 열 | 들어 있는 것 |
|---|---|---|
| `raw.card_spending` | `strd_yymm, sido_nm, ccg_nm, gender_cd, age_cd, tp_buz_no, tp_buz_nm, amt, cnt` | CSV 열 그대로(이름만 소문자). 성별 3 · x, 업종명 공백까지 |
| `raw.future_population` | `source_file, province, region, sex, age_label, age_detail, year, population` | 5세 · 1세 · 합계 행, '0 - 4세' · '0~4세' 같은 원본 표기 그대로. `age_detail`은 KOSIS 엑셀의 연령별(2)('소계' 또는 '0세') |

**왜 한 행씩 INSERT하지 않고 COPY인가요?** 수십만 행을 한 행씩 넣으면 요청이 수십만 번 오갑니다. COPY는 CSV 한 덩어리를 한 번에 보내서 훨씬 빠릅니다.

## 써 보고 확인한 것

원본 데이터, 2026-10-21:

| 확인 | 결과 |
|---|---|
| `raw.card_spending` | 242,574행 · 금액 17,224,900,070,000원 (Bronze 원본과 같음) |
| `raw.future_population` | 577,680행 (서울 190,008 · 부산 153,816 · 경기 233,856), 빈 값 0 |
| 첫 적재 / 두 번째 | 9초 '신규' / 3초 '변경 없음' |
| **SQL만으로 Silver 숫자** | `WHERE gender_cd IN ('1','2') AND age_cd IN ('1'..'6')` → **159,235행 · 14,890,593,590,000원** = 파이썬 Silver와 같음 |
| 파이프라인 | `--object-store --warehouse --compare`: 왕복 지문 60개 · raw 대사 2개 통과, 공모전 결과표 6/6 |
| 합성 데이터 | `raw_synthetic`에 179,702행 · 577,680행 (원본 `raw`는 그대로). 장래인구 행 수가 원본과 같아 합성 데이터가 형식을 그대로 재현함을 다시 확인 |

- **트랜잭션 되돌리기를 실제로 봤습니다.** 처음 실행에서 `COMMENT ON TABLE ... IS %s`가 문법 오류로 실패했는데(COMMENT 문은 값 자리를 받지 않음), 그 직전에 만든 스키마 · 표 · 기록이 모두 되돌려져 아무것도 남지 않았습니다. `sql.Literal`로 고쳤습니다.
- **되돌리기 테스트를 한 번 고쳤습니다.** 처음 테스트는 원본을 읽는 단계에서 실패하게 했는데, 그건 표를 지우기 *전*이라 되돌리기를 확인한 게 아니었습니다. 숫자 열에 글자를 넣어 표를 지우고 다시 만든 *뒤* COPY에서 실패하게 바꿨고, 이전 행 수가 그대로 남는 것을 확인했습니다.
- 누가 raw 표에서 행을 지우면, 원본 지문이 같아도 행 수가 달라 다시 적재합니다 (테스트로 확인).
- 테스트는 매번 새 스키마(`raw_test_xxxx`)를 만들어 쓰고 지워서, 원본이 든 `raw`를 건드리지 않습니다.

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| Silver Parquet을 그대로 DB에 넣기 | 그러면 거르기 · 코드 바꾸기가 이미 파이썬에서 끝나 있어서, dbt가 할 일(Silver 규칙)이 없어집니다 |
| pandas `to_sql` (SQLAlchemy) | 의존성이 늘고, 대량 적재가 COPY보다 느립니다 |
| 한 행씩 INSERT | 수십만 번 요청이 오가 느립니다 |
| 매번 지우고 다시 넣기만 | 같은 원본이어도 매번 시간이 들고, '언제 바뀌었나' 기록이 흐려집니다 |
| DuckDB (파일형 DB) | 가볍지만 여러 서비스(dbt, 대시보드, Airflow)가 함께 붙는 서버형 웨어하우스 구조를 보여 주려는 목적과 맞지 않습니다 |

## 스스로 점검할 질문

<details><summary>Q1. raw 스키마에 원본을 '거르지 않고' 넣는 이유는?</summary>

거르는 규칙(개인 결제만, 5세 구간만)을 dbt에서 SQL로 보이게 하고 테스트하기 위해서입니다. raw에 걸러진 데이터를 넣으면 그 규칙이 파이썬 안에 숨어 버리고, 규칙이 바뀌었을 때 원본을 다시 적재해야 합니다. raw는 Bronze처럼 '받은 그대로'에 가깝게 둡니다.
</details>

<details><summary>Q2. 트랜잭션이 왜 중요한가? 이 프로젝트에서 실제로 어떤 일이 있었나?</summary>

여러 단계(표 지우기 → 만들기 → 넣기 → 확인 → 기록)를 '모두 되거나 모두 안 되거나'로 묶어 줍니다. 중간에 실패해도 반쯤 지워진 표가 남지 않습니다. 실제로 COMMENT 문법 오류로 실패했을 때, 그 전에 만든 스키마와 표가 모두 되돌려져 깨끗한 상태로 남았습니다.
</details>

<details><summary>Q3. 같은 원본인지 판단할 때 지문만 보지 않고 행 수 · 합계도 보는 이유는?</summary>

원본은 그대로인데 DB 쪽 표가 바뀐 경우(누가 행을 지움)를 잡기 위해서입니다. 지문만 보면 '변경 없음'으로 넘어가서 틀린 표가 계속 쓰입니다.
</details>

<details><summary>Q4. 파이썬과 dbt의 역할을 어떻게 나눴나?</summary>

파일 형식 문제(인코딩, 깨진 따옴표, 병합 셀)는 파이썬이 읽어서 표로 만들고, 그 뒤의 규칙(거르기, 코드 → 이름, 집계, 판정)은 dbt가 SQL로 합니다. SQL로 할 수 없는 통계 검정과 최적화는 파이썬에 남깁니다.
</details>
