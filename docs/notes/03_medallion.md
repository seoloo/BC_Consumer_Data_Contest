# 03. 메달리온 아키텍처 (Bronze → Silver → Gold)

## 한 줄 요약

데이터를 '얼마나 다듬어졌는가'에 따라 세 층으로 나눠 저장합니다. 각 층은 바로 앞 층만 읽어서, 문제가 생기면 어느 층에서 생겼는지 알 수 있고 그 층부터 다시 만들면 됩니다.

| 층 | 들어 있는 것 | 이 프로젝트에서 |
|---|---|---|
| Bronze | 원본 그대로 + 적재 영수증 | 원본 8종 복사본, `_manifest.json` (파일마다 SHA-256 지문 · 크기 · 행 수 · 상태) |
| Silver | 정제 · 표준화한 표 (아직 집계 전) | Parquet 6개: 카드 결제, 장래인구, 주민등록인구, 서울 생활인구 비중, 부산 거주 노출, 경기 유동인구 비중 |
| Gold | 분석 결과 | Parquet 16개: 연령별 소비구조, Future Stress, 4유형, 검증, 방어 전략, 재조정 결과, 발표용 표 6개 |

## 왜 필요했나

- 노트북 시절에는 `data/processed/`에 중간 CSV가 30개 넘게 쌓였습니다. 어떤 파일이 어떤 단계에서 나왔는지, 최신인지 알기 어려웠습니다.
- 원본을 읽으면서 바로 정제하고 바로 분석해서, 결과가 이상할 때 "원본이 이상한지, 정제가 이상한지, 계산이 이상한지" 나눠 볼 수 없었습니다.
- 원본에 손을 댄 흔적(인코딩 변환, 열 삭제)이 남으면, 나중에 처음부터 다시 만들 수 없습니다.

## 어떻게 했나

코드: `src/future_stress/medallion.py`, 실행 순서: `pipeline.run_pipeline()`

```text
build_bronze(raw → bronze)     원본을 수정 없이 복사, 지문이 같으면 건너뜀
build_silver(bronze → silver)  Bronze만 읽어 정제 · 표준화 (코드값 → 이름, 인코딩, 별칭 통일)
build_gold(silver → gold)      저장된 Silver Parquet만 읽어 분석
run_quality_checks(...)        층 사이 건수 · 금액이 맞는지 10개 검사 (04 참고)
```

- **각 층은 바로 앞 층만 읽습니다.** Gold는 메모리에 있는 Silver가 아니라 디스크에 저장된 Silver Parquet을 다시 읽습니다. 그래야 "Silver만 있으면 Gold를 다시 만들 수 있다"가 실제로 보장됩니다.
- **Bronze는 원본을 바꾸지 않습니다.** 인코딩 변환도 Silver에서 합니다. Bronze만 남아 있으면 언제든 Silver부터 다시 만들 수 있습니다.
- **Silver는 '같은 단위, 표준 이름'까지만** 만듭니다. 성별 코드 1/2 → 남성/여성, 연령 코드 → 6개 연령대, '20대미만' → '20대이하'. 집계(합계, 비중)는 Gold에서 합니다.
- 층 폴더(`data/bronze`, `data/silver`, `data/gold`)는 원본에서 나온 데이터라 git에 올리지 않습니다.

## 써 보고 확인한 것

- 원본 실행 결과: Bronze 원본 242,574행 → Silver 159,235행 (개인이 아닌 결제 83,339행 제외) → Gold 금액 합계 14.89조 원. 층 사이 숫자가 모두 맞았습니다.
- 카드 결제 Silver가 CSV 16.4MB에서 Parquet 1.4MB로 줄었습니다 (06 참고).
- 층을 나눈 뒤에도 발표 결과는 6/6 그대로였습니다.
- 합성 데이터로도 같은 층 구조가 그대로 돌아갑니다 (`data/synthetic/bronze ...`). 층 구조가 원본에 묶여 있지 않다는 뜻입니다.

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| 원본 → 결과를 한 번에 | 문제가 어디서 생겼는지 나눠 볼 수 없고, 중간부터 다시 돌릴 수 없습니다 |
| 단계마다 CSV로 저장 (예전 방식) | 파일이 계속 늘고, 다시 읽을 때 타입이 바뀌고(문자 '01' → 숫자 1), 인코딩이 섞였습니다 |
| 층을 더 잘게 (5~6층) | 지금 데이터 크기와 단계 수에는 세 층이면 충분합니다. 층이 늘면 대사할 곳도 늘어납니다 |

## 스스로 점검할 질문

<details><summary>Q1. Bronze에서 인코딩 변환조차 하지 않는 이유는?</summary>

Bronze는 "받은 그대로"의 기록이라, 나중에 정제 규칙이 틀린 것을 알았을 때 Bronze부터 다시 만들 수 있어야 합니다. 변환한 것을 저장하면 원래 무엇을 받았는지 잃어버립니다.
</details>

<details><summary>Q2. Silver와 Gold의 경계는 어디인가?</summary>

Silver는 원본과 같은 단위(행 하나 = 결제 집계 한 칸)에서 이름 · 코드 · 타입만 표준화한 것입니다. 합치고, 나누고, 비율을 내고, 판정하는 순간부터 Gold입니다.
</details>

<details><summary>Q3. Gold가 메모리의 Silver 대신 저장된 Silver 파일을 다시 읽는 이유는?</summary>

저장 · 읽기 과정에서 생기는 문제(타입 변화, 열 누락)까지 매번 거치게 하려는 것입니다. 메모리 객체를 넘기면 "Silver 파일만으로 Gold를 다시 만들 수 있다"가 확인되지 않습니다.
</details>
