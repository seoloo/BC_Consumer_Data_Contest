# 20. 운영 매뉴얼 · 상태 점검

## 한 줄 요약

띄우기 · 매달 할 일 · 지난달 다시 돌리기 · 실패했을 때 · 다시 만들기를 [운영 매뉴얼](../operations.md) 한 곳에 모았습니다. 서비스 다섯 군데를 한 번에 살펴보는 `python -m future_stress.health`를 만들어 매뉴얼의 첫 단계로 두었습니다. 매뉴얼의 명령은 모두 실제로 돌려 봤고, 일부러 저장소를 꺼서 실패와 복구까지 따라 해 봤습니다.

## 왜 필요했나

- 서비스가 다섯 개(객체 저장소 · PostgreSQL · dbt · Airflow · 대시보드)로 늘었습니다. 무엇이 무엇에 기대는지 모르면, 대시보드가 비었을 때 어디부터 봐야 할지 알 수 없습니다.
- 지금까지 '어떻게 돌리는지'는 README · 기록 · 코드 주석에 흩어져 있었습니다. 한 달 뒤의 나도, 처음 보는 사람도 같은 순서로 따라 할 수 있어야 합니다.
- 실패는 언젠가 납니다. 실패했을 때 할 일이 미리 적혀 있어야, 당황해서 데이터를 지우는 일이 없습니다.

## 어떻게 했나

**상태 점검 `future_stress.health`**

| 항목 | 정상 | 경고 | 실패 |
|---|---|---|---|
| .env 계정 | S3 · PostgreSQL 계정 있음 | | 없음 → `local_env` |
| 객체 저장소 | 최근 배치 폴더에 영수증(`_manifest.json`) 있음 | | 연결 안 됨 / 배치 없음 / 영수증 없음(올리다 멈춤) |
| 새 원본 | 원본 폴더의 최신 배치까지 저장소에 있음 | 새 배치가 아직 처리 전 / 원본 없는 PC | |
| raw 적재 | 두 표 모두 적재 기록 (상태 · 행 수 · 시각) | | 기록 없음 |
| gold 표 | dbt gold 9개 표가 모두 있고 비어 있지 않음 | | 없거나 빈 표 → `dbt build` |
| Airflow (원본만) | 마지막 실행 성공 · 떠 있음 | 꺼져 있음 / 한 번도 안 띄움 | 마지막 실행 실패 (실패한 단계 이름까지) |

- 위에서부터 차례로 기댑니다. 저장소가 꺼져 있으면 '새 원본'은 판단하지 않는다고 따로 표시합니다(처음에는 '처리 전'이라고 잘못 알려 줘서 고침).
- 연결 오류가 나도 멈추지 않고 나머지 항목을 계속 봅니다.
- 계정 값은 출력하지 않고 '있음 · 없음'만 봅니다.
- 한글 이름은 터미널에서 두 칸을 차지해서, 글자 수가 아니라 칸 수로 줄을 맞춥니다.

**운영 매뉴얼 [docs/operations.md](../operations.md)**: 구성 → 처음 설치 → 평소 띄우기 · 끄기 → 매달 할 일 → 지난달 다시 돌리기 → 실패했을 때(단계별 증상 · 원인 · 할 일) → 다시 만들기 → 가끔 하는 일 → 매달 점검표.

## 써 보고 확인한 것

| 확인 | 결과 |
|---|---|
| 원본 · 합성 `health` | 모두 정상, 종료 코드 0 |
| **객체 저장소를 끄고** `health` | `객체 저장소 실패 → docker compose up -d`, 종료 코드 1 |
| 저장소가 꺼진 채 Airflow 실행 | `has_new_batch` · `build_bronze` 성공 → `upload` 2번 시도 후 실패 → 뒤 6단계 '업스트림 실패'. `health`가 `Airflow 실패 · 실패한 단계 upload`로 보여 줌 |
| 저장소를 켜고 화면에서 '실패한 작업만 지우기' | 6단계만 다시 돌아 모두 성공. 앞 2단계는 다시 돌지 않음 |
| PowerShell로 손 실행 (`dags trigger -c '{\"batch_month\":202606}'`) | 8단계 성공 |
| PowerShell로 한 달 backfill (`--from-date 2026-07-01 --to-date 2026-07-01 --reprocess-behavior completed`) | 7월 1일 실행(배치 202606)을 **새로 만들지 않고 지운 뒤 다시** 돌려 성공 |
| 테스트 8개 | 판단 함수 7개 + 실제 서비스(합성) 1개 |

**알게 된 것**

1. **Airflow 3의 손 실행은 논리 날짜가 비어 있습니다.** 처음에는 '마지막 실행'을 논리 날짜 순으로 골라서, 방금 실패한 손 실행이 빠지고 예전 성공 실행이 보였습니다. 실행 예정 시각(`run_after`) 순으로 바꿨습니다.
2. **Airflow CLI의 `tasks clear`는 날짜로 고릅니다.** 논리 날짜가 없는 손 실행에는 맞지 않아서, 매뉴얼에는 화면의 '실패한 작업만 지우기'와 '같은 배치 월로 새로 실행'(멱등이라 앞 단계는 '변경 없음') 두 가지를 적었습니다.
3. **PostgreSQL 비밀번호는 볼륨을 처음 만들 때만 정해집니다.** `.env`를 새로 만들면 기존 DB에 접속할 수 없습니다. 매뉴얼의 '다시 만들기'에 적었습니다.

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| Grafana · Prometheus 모니터링 | 컨테이너 2개가 더 늘고, 월 1회 배치에 실시간 지표는 과합니다. 지금 필요한 건 '지금 무엇이 멈췄나' 한 번 보기입니다 |
| Airflow 실패 알림(이메일 · Slack) | 메일 서버 · 웹훅 계정이 필요하고 이 PC 전용 환경입니다. 실패는 Airflow 화면과 `health`로 보고, 알림은 [13](13_planned.md)에 남깁니다 |
| `docker compose ps`만 보기 | 컨테이너가 떠 있는지만 알 수 있고, 표가 비었는지 · 새 원본이 처리됐는지는 모릅니다 |
| DB 정기 백업(pg_dump) | 모든 데이터를 원본에서 다시 만들 수 있어 백업할 이유가 작습니다. 지켜야 할 것은 원본입니다 |

## 스스로 점검할 질문

<details><summary>Q1. 상태 점검에서 '경고'와 '실패'를 왜 나눴나?</summary>

실패는 지금 무언가가 망가져 결과를 믿을 수 없거나 다음 실행이 실패하는 상태이고, 경고는 정상일 수도 있지만 사람이 한 번 봐야 하는 상태입니다(예: Airflow를 일부러 꺼 둠, 새 원본이 아직 처리 전). 모두 실패로 두면 늘 빨간 줄이 보여 진짜 실패를 놓칩니다. Airflow의 '건너뜀'을 실패로 두지 않은 것과 같은 이유입니다.
</details>

<details><summary>Q2. 백업 없이 괜찮은가?</summary>

이 파이프라인은 같은 원본이면 같은 결과가 나오고(멱등), 층마다 숫자를 맞춰 봅니다. 그래서 DB · 저장소를 잃어도 원본에서 다시 만들면 같은 결과가 됩니다. 지켜야 할 것은 원본뿐이고, 원래 위치에도 사본을 둡니다. 다시 만들 수 없는 것(Airflow 실행 기록)은 잃어도 결과에는 영향이 없습니다.
</details>

<details><summary>Q3. 실패한 단계부터 다시 돌릴 수 있는 이유는?</summary>

단계마다 결과를 다음 단계가 읽을 수 있는 곳(파일 · 저장소 · DB)에 남기고, 단계마다 다시 돌려도 결과가 같게 만들었기 때문입니다. 그래서 실패한 `upload`부터 다시 돌려도 되고, 아예 처음부터 다시 돌려도 앞 단계는 '변경 없음'으로 지나갑니다.
</details>

<details><summary>Q4. 매뉴얼의 명령을 왜 직접 돌려 봤나?</summary>

적어 둔 명령이 틀리면 정작 필요할 때 매뉴얼을 믿을 수 없습니다. 실제로 돌려 보면서 `_quality_report.csv` 경로를 바로잡았고, PowerShell에서 JSON을 넘기는 따옴표 모양과 backfill이 같은 실행을 지우고 다시 돈다는 점을 확인했습니다.
</details>
