# 18. Airflow (월 배치)

## 한 줄 요약

원본 도착 확인 → Bronze → 객체 저장소 → raw → dbt · 파이썬 → 비교를 **매달 1일(한국 시간)에 지난달 배치를 처리하는 DAG**로 묶었습니다. 단계마다 나눠 두어 어디서 멈췄는지 보이고 그 단계부터 다시 돌릴 수 있으며, 같은 달을 다시 돌려도 중복이 생기지 않습니다.

## 결정 기록

| 날짜 | 결정 | 이유 |
|---|---|---|
| 2026-10-21 | CI 다음으로 Airflow | 그때는 GitHub Actions를 11월부터 쓸 수 있다고 판단해 월 배치(4-2)를 먼저 함 (실제로는 CI가 처음부터 돌고 있었음, [17](17_ci.md)) |
| 2026-10-21 | 이 PC에 있던 공식 이미지(3.1.7) 위에 얹기 | 3GB짜리 이미지를 새로 받지 않음. 프로젝트 의존성은 이 PC의 .venv와 같은 버전으로 고정 |
| 2026-10-21 | dbt는 Airflow 안의 별도 가상환경 (1.9.0) | Airflow와 dbt의 의존성이 부딪히지 않게. dbt 컨테이너와 같은 버전. Airflow가 Docker를 직접 부르려면 docker.sock(사실상 PC 관리자 권한)을 넘겨야 해서 피함 |
| 2026-10-21 | `airflow standalone` (한 컨테이너) | 스케줄러 · 화면 · DAG 읽기를 한 컨테이너에. 운영용은 아니지만, 이미 다른 프로젝트 컨테이너가 많이 떠 있는 이 PC의 메모리에 맞춤 |
| 2026-10-21 | Airflow 기록 DB는 같은 PostgreSQL의 `airflow` 데이터베이스 | PostgreSQL 컨테이너를 하나 더 띄우지 않고, 분석 데이터(`future_stress`)와는 데이터베이스를 나눠 섞이지 않게 |
| 2026-10-21 | 평소에는 띄우지 않음 (`profiles: ["airflow"]`) | 약 1GB 메모리. 필요할 때만 `docker compose --profile airflow up -d` |
| 2026-10-21 | DAG는 얇게, 일은 `orchestration.py`가 | Airflow 없이도 함수를 테스트할 수 있게. 명령줄 · 테스트 · Airflow가 같은 함수를 씀 |
| 2026-10-21 | 배치 월 = 실행 시각(한국 시간)의 지난달 | 7월 1일 0시 실행이 6월 배치를 처리. Airflow가 넘겨주는 UTC를 그대로 읽으면 한 달이 어긋나는 것을 실제로 겪음 (아래) |

## 왜 필요했나

- 지금까지는 사람이 명령을 순서대로 쳤습니다. 매달 새 데이터가 들어온다면 매번 같은 순서를 기억하고 실행해야 합니다.
- 한 명령(`pipeline`)으로 다 돌리면, 중간에 실패했을 때 어디서 멈췄는지 찾고 처음부터 다시 돌려야 합니다.
- 지난달 결과를 다시 만들어야 할 때(규칙을 고쳤을 때) 어느 달을 어떻게 돌렸는지 기록이 필요합니다.

## 어떻게 했나

```text
has_new_batch ─▶ build_bronze ─▶ upload ─▶ download ─▶ load_raw ─┬▶ dbt_build ─────┬▶ compare
                                                                  └▶ python_layers ─┘
```

| 단계 | 하는 일 | 함수 |
|---|---|---|
| `has_new_batch` | 이 배치 월의 원본이 왔나? 없으면 뒤 단계는 '건너뜀'(실패 아님) | `has_new_batch()` |
| `build_bronze` | 원본 → 로컬 Bronze (지문 영수증) | `step_build_bronze()` |
| `upload` · `download` | 객체 저장소 `batch_month=YYYYMM/`에 올리고 받아 지문 확인 | `step_upload()` · `step_download()` |
| `load_raw` | PostgreSQL raw 적재 (대사가 틀리면 되돌림) | `step_load_raw()` |
| `dbt_build` | dbt Silver · Gold + 테스트 49개 | `step_dbt_build()` |
| `python_layers` | 파이썬 Silver · Gold · 대사 · 통계 검정 · 결과 CSV | `step_python_layers()` |
| `compare` | dbt = 파이썬? 다르면 실패 | `step_compare()` |

- dbt와 파이썬은 서로 다른 곳(DB 스키마 / 파일)에 쓰므로 **동시에** 돌고, 둘 다 끝나야 비교합니다.
- 일시적인 연결 오류에 대비해 단계마다 1분 뒤 한 번 더 시도합니다 (`retries=1`).
- 같은 `data/` 폴더를 쓰므로 한 번에 한 실행만 (`max_active_runs=1`).
- 손으로 돌릴 때는 `batch_month`를 직접 줄 수 있습니다 (예: 202606).

**배치 월이란?** 한 번에 도착한 원본 묶음의 이름입니다. BC카드 파일 이름(`bc_card_<시작월>_<끝월>.csv`)의 끝월로 정합니다. 공모전 데이터는 2026.01 ~ 06이 **한 번에 온 묶음 하나**라서 배치 월은 202606 하나뿐입니다. 그래서 2 ~ 6월 1일 실행(배치 202601 ~ 202605)은 '새 원본 없음'으로 건너뛰고, 7월 1일 실행(배치 202606)만 실제로 처리합니다. 다음 달 원본이 오면 같은 DAG가 그 달을 처리합니다.

> **바로잡음 (2026-10-22).** 위 마지막 문장은 이 기록을 쓸 때의 코드로는 사실이 아니었습니다. 카드 원본 파일 이름과 분석 기간(1 ~ 6월)이 고정되어 있어, 7월 파일이 와도 예전 6개월을 다시 처리하고 성공으로 끝났습니다. [21 새 달 원본 처리](21_monthly_batch.md)에서 고쳐, 지금은 새 달이 오면 분석 기간이 최근 6개월로 옮겨 갑니다.

## 써 보고 확인한 것

| 확인 | 결과 |
|---|---|
| DAG 읽기 | 읽기 오류 없음, 단계 8개 |
| 6월 배치 (`airflow dags test`, batch_month=202606) | 8단계 모두 성공, **67초**. Bronze 60개 · raw 2개 표 '변경 없음', dbt 65단계 통과, Silver 321,494칸 · Gold 125,805칸 일치 |
| 다시 돌리기 | 이미 처리한 원본이라 Bronze · 저장소 · raw가 모두 '변경 없음' (중복 없음) |
| **backfill** 2월 1일 ~ 7월 1일 실행 (스케줄러) | 2 ~ 5월 1일 실행(배치 202601 ~ 202604): 원본 확인만 성공, 나머지 7단계 **건너뜀** / 7월 1일 실행(배치 202606): **8단계 모두 성공** |
| 켜자마자 스케줄러가 만든 실행 | 10월 1일 실행(배치 202609): 건너뜀. `catchup=False`라 지난 달들을 한꺼번에 돌리지 않고 가장 최근 한 번만 만듦 |

6월 1일 실행(배치 202605)은 앞서 `airflow dags test`로 같은 날짜의 실행을 만들어 둔 상태라 backfill이 새로 만들지 않았습니다. 같은 날짜의 실행은 하나만 있을 수 있기 때문입니다.

`airflow dags test`는 DAG가 꺼져(pause) 있을 때만 씁니다. 켜져 있으면 상시로 도는 스케줄러도 같은 실행의 단계를 집어 들어 같은 단계가 두 번 동시에 돌 수 있습니다(2026-10-22 실제로 겪음, [21](21_monthly_batch.md)). 켜진 DAG는 `airflow dags trigger`로 실행합니다.

**실제로 부딪힌 문제 세 가지**

1. **Airflow가 뜨자마자 멈췄습니다.** 공식 이미지는 명령을 실행하기 *전에* 기록용 DB 접속을 20번 확인하는데, 그 DB(`airflow`)는 명령 안의 스크립트가 만들기 때문에 처음에는 없었습니다. 시작 확인을 끄고(`CONNECTION_CHECK_MAX_COUNT=0`) 스크립트가 DB를 만든 뒤 Airflow가 뜨게 했습니다.
2. **dbt 단계가 권한 오류로 실패했습니다.** 저장소의 `dbt/logs` · `dbt/target`은 dbt 컨테이너(root)가 만든 폴더라 Airflow 사용자(uid 50000)가 쓸 수 없었습니다. Airflow 안의 dbt는 결과 · 기록을 Airflow 자기 폴더에 쓰게 했습니다(`DBT_TARGET_PATH` · `DBT_LOG_PATH`). 두 컨테이너가 같은 폴더를 덮어쓰는 일도 함께 막힙니다.
3. **배치 월이 한 달씩 어긋났습니다.** Airflow 3의 `@monthly`는 실행 시각을 구간 시작으로 넘겨주는데(6월 1일 0시 KST), 이 값이 UTC(5월 31일 15시)로 들어와 그대로 읽으면 202605가 됩니다. 또 설명은 '지난달 배치'인데 코드는 실행한 달을 쓰고 있었습니다. backfill 로그를 보다가 찾았고, 한국 시간으로 바꾼 뒤 지난달을 세게 고쳐 테스트로 고정했습니다(`batch_month_for_run`).

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| Windows 작업 스케줄러 + 스크립트 | 단계별 성공 · 실패 · 재시도 기록과 화면이 없고, 지난달 다시 돌리기를 직접 만들어야 합니다 |
| 한 단계(`pipeline` 명령 하나)로 | 실패 위치가 안 보이고 처음부터 다시 돌려야 합니다 |
| Airflow 정식 구성 (스케줄러 · API 서버 · DAG 처리기 · triggerer 각각) | 컨테이너가 4 ~ 5개로 늘어 이 PC 메모리에 부담. 구조는 같아서 나중에 나누기 쉽습니다 |
| `DockerOperator`로 dbt 컨테이너 실행 | Airflow에 docker.sock을 넘겨야 해서(사실상 PC 관리자 권한) 피했습니다 |
| Prefect · Dagster | 이 PC에 Airflow 이미지가 이미 있고 다른 프로젝트도 Airflow를 써서, 운영 방식을 하나로 맞출 수 있습니다. 자료와 사례도 가장 많습니다 |

## 스스로 점검할 질문

<details><summary>Q1. DAG를 단계로 나누면 무엇이 좋은가?</summary>

어느 단계에서 실패했는지 화면에 바로 보이고, 그 단계부터 다시 돌릴 수 있습니다. 단계마다 재시도 · 시간 제한을 따로 줄 수 있고, 서로 기다릴 필요 없는 단계(dbt와 파이썬)는 동시에 돌립니다.
</details>

<details><summary>Q2. 데이터가 없는 달은 왜 '실패'가 아니라 '건너뜀'인가?</summary>

새 원본이 아직 안 온 것은 오류가 아니라 정상 상태입니다. 실패로 두면 매달 경보가 울려 진짜 실패를 놓치게 됩니다. short_circuit 단계가 False를 돌려주면 뒤 단계는 skipped로 끝나고, 실행 자체는 성공입니다.
</details>

<details><summary>Q3. backfill(지난달 다시 돌리기)이 안전하려면 무엇이 필요한가?</summary>

같은 달을 다시 돌려도 결과가 같아야 합니다(멱등성). 이 프로젝트는 지문이 같으면 '변경 없음'으로 건너뛰고, raw 적재는 트랜잭션으로 지우고 다시 넣으며, 객체 저장소는 배치 월 폴더 단위라 다른 달을 건드리지 않습니다. 그리고 한 번에 한 실행만 돌게 해서 같은 폴더를 동시에 쓰지 않게 했습니다.
</details>

<details><summary>Q4. 배치 월을 정할 때 시간대가 왜 문제가 되었나?</summary>

Airflow는 실행 시각을 UTC로 넘겨줍니다. 한국 시간 1일 0시는 UTC로 전날 15시라서, 그대로 달을 읽으면 한 달이 어긋납니다. 먼저 한국 시간으로 바꾼 뒤 지난달을 세도록 하고, 이 경계(UTC 6월 30일 15시 → 202606)를 테스트로 고정했습니다.
</details>
