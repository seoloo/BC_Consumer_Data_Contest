# 14. 객체 저장소 SeaweedFS (Bronze 보관)

## 한 줄 요약

Bronze 원본을 이 PC 폴더 대신 **S3 호환 객체 저장소(SeaweedFS)** 의 버킷에 배치 월별로 올리고, Silver는 저장소에서 다시 받은 파일로 만듭니다. 코드는 S3 표준 라이브러리(boto3)로만 짜서 저장소를 바꿔도 접속 주소만 바꾸면 됩니다.

## 결정 기록

| 날짜 | 결정 | 이유 · 사용자 말 |
|---|---|---|
| 2026-10-21 | MinIO 대신 SeaweedFS | 계획은 MinIO였지만 `minio/minio` 이미지를 받으려 하자 "접근 거부"가 나왔습니다. MinIO는 2025-10 무료판 이미지 배포를 멈췄고 2026-09 Docker Hub에서 이미지가 지워졌습니다. 후보(SeaweedFS · RustFS · Garage · Chainguard MinIO)를 비교해 추천했고, 사용자 "seaweedFS로 진행하되, 왜 이 기술을 사용했는지 … 기록해줘" |
| 2026-10-21 | 다른 프로젝트 컨테이너와 따로 띄움 | 같은 PC의 `Sports_Prediction`도 SeaweedFS를 쓰지만, 데이터가 섞이지 않고 한쪽을 지워도 다른 쪽이 영향받지 않게 컨테이너 · 볼륨 · 포트(59100)를 나눔 |
| 2026-10-21 | 합성 데이터는 별도 버킷(`bronze-synthetic`) | 합성 데이터로 실행했더니 원본과 파일 이름이 같아 원본 객체를 덮어썼음(아래 '써 보고 확인한 것'). 버킷을 나눔 |

## 왜 필요했나

- Bronze가 `data/bronze/` 폴더라 이 PC에서만 보였습니다. Phase 3 · 4에서 Airflow, dbt 같은 다른 서비스가 같은 원본을 읽으려면 서버 형태의 저장소가 필요합니다.
- 실무의 데이터 레이크는 원본을 S3 같은 객체 저장소에 쌓습니다. 같은 구조를 비용 없이 로컬에서 만들어 보고 싶었습니다.
- 한 달 데이터에 문제가 생겼을 때 그 달만 다시 올리고 다시 처리할 수 있는 구조가 필요했습니다.

## 어떻게 했나

| 무엇 | 어디 | 핵심 |
|---|---|---|
| 저장소 띄우기 | `docker-compose.yml` | `chrislusf/seaweedfs:4.48` 버전 고정, `127.0.0.1:59100`(이 PC에서만 접속), 데이터는 Docker 볼륨, healthcheck |
| 계정 키 | `object_store.init_env()`, `.env` | 이 PC 전용 키를 무작위로 만들어 `.env`에만 저장(화면에 출력 안 함). 컨테이너는 시작할 때 이 키로 계정 설정 파일을 만듦 |
| 저장소 창구 | `object_store.ObjectStore` | boto3 클라이언트를 밖에서 받음(의존성 주입) → 테스트는 가짜 클라이언트로 Docker 없이 |
| 올리기 | `upload_bronze()` | 키 = `batch_month=202606/<원본 종류>/<파일>`. 객체 메타데이터에 SHA-256을 적고, 같으면 안 올림 |
| 받기 | `download_bronze()` | 받은 파일의 지문을 영수증(`_manifest.json`)과 다시 맞춤. 다르면 `DataQualityError`로 멈춤 |
| 파이프라인 | `pipeline --object-store` | 로컬 Bronze → 저장소에 올림 → 저장소에서 `data/bronze_cache/`로 받음 → 그걸로 Silver. 대사 보고서에 '객체 저장소 왕복 지문' 줄 추가 |

**왜 `batch_month=202606/` 같은 이름인가요?** 데이터 레이크에서 흔히 쓰는 파티션 이름 방식입니다(`이름=값`). 폴더 이름만 보고 무엇으로 나눴는지 알 수 있고, 나중에 Spark · DuckDB · Athena 같은 도구가 이 이름을 그대로 열로 읽을 수 있습니다.

**왜 원본 파일을 달마다 쪼개지 않았나요?** 카드 원본 한 파일에 6개월(202601~202606)이 들어 있습니다. Bronze는 받은 그대로 두는 층이라 쪼개지 않고, 이 묶음 전체를 '202606 배치'로 올렸습니다. 매달 새 파일이 오면 새 배치 폴더가 생기는 구조입니다.

## 써 보고 확인한 것

원본 데이터, 2026-10-21:

| 확인 | 결과 |
|---|---|
| 올린 것 | Bronze 파일 60개(약 132MB) + 영수증 1개 |
| 왕복 지문 | 60개 모두 영수증과 같음 |
| 발표 결과 | `--object-store --compare` 6/6 일치 (저장소를 거쳐도 숫자 그대로) |
| 두 번째 실행 | 데이터 파일 60개 모두 '변경 없음', 영수증만 '변경'(적재 시각이 들어 있어서) |
| 걸린 시간 | 저장소 없이 17초 / 첫 실행(올리기 포함) 24초 / 두 번째부터 18초 |

- **같은 파일을 다시 올리지 않는 효과:** 두 번째부터는 저장소를 거쳐도 1초 정도만 더 걸렸습니다. 매번 132MB를 다시 올렸다면 첫 실행처럼 7초가 더 걸립니다.
- **지문 비교가 실제로 사고를 잡았습니다.** 합성 데이터로 `--synthetic --object-store`를 돌렸더니, 원본과 파일 이름 · 버킷 · 배치 월이 같아서 원본 객체 61개가 합성 데이터로 덮어써졌습니다. 그 뒤 원본으로 다시 돌리자 업로드 결과가 **'변경 61'** 로 나와 바로 알아챘고, 원본이 다시 올라가 6/6이 그대로 나왔습니다. 그 뒤 합성 데이터는 `bronze-synthetic` 버킷을 쓰게 바꿨습니다.
- Docker가 없어도 테스트 5개(가짜 클라이언트)가 돌고, 컨테이너가 떠 있으면 실제 SeaweedFS 왕복 테스트 1개가 더 돕니다 (`pytest -m integration`). 없으면 건너뜁니다.
- Docker를 켜지 않고 실행하면 긴 오류 대신 "`docker compose up -d`로 띄운 뒤 다시 실행해 주세요" 한 줄이 나옵니다.

## 다른 방법과 고르지 않은 이유

| 방법 | 고르지 않은 이유 |
|---|---|
| MinIO | 무료판 이미지가 Docker Hub에서 지워짐 (2026-09) |
| Chainguard MinIO 이미지 | 무료로는 `latest`만 받을 수 있어 버전 고정 불가 → 재현성 원칙과 맞지 않음 |
| RustFS | 웹 화면이 좋지만 새 프로젝트라 버전이 빨리 바뀜 |
| Garage | 처음 설정(노드 · 레이아웃)이 더 번거로움 |
| AWS S3 | 계정 · 비용이 필요하고 다른 사람이 그대로 따라 하기 어려움 |
| 로컬 폴더 유지 | 다른 서비스와 공유할 수 없음 |

**배운 점:** 특정 제품이 아니라 **S3 API라는 약속**에 맞춰 코드를 짜 둔 덕분에, 제품이 사라져도 접속 주소만 바꾸면 됐습니다. 이번 MinIO 일이 그 이유를 직접 보여 준 사례입니다.

## 스스로 점검할 질문

<details><summary>Q1. 객체 저장소와 일반 폴더(파일 시스템)는 무엇이 다른가?</summary>

폴더는 그 PC의 운영체제가 관리하고, 객체 저장소는 네트워크 너머의 서버가 버킷 · 키 단위로 관리하며 HTTP API(S3 API)로 올리고 받습니다. 그래서 여러 서비스가 같은 저장소를 함께 쓸 수 있고, 저장 용량을 서버 쪽에서 늘릴 수 있습니다. 대신 파일을 부분 수정하지 못하고 통째로 다시 올려야 합니다.
</details>

<details><summary>Q2. 같은 파일인지 어떻게 판단했나? 왜 S3의 ETag를 쓰지 않았나?</summary>

올릴 때 내용의 SHA-256을 객체 메타데이터(`x-amz-meta-sha256`)에 적어 두고, 다음에 올리기 전에 `head_object`로 그 값을 비교합니다. ETag는 업로드 방식(여러 조각으로 나눠 올리기 등)에 따라 MD5가 아닐 수 있고 저장소마다 계산이 달라서, 직접 정한 지문을 쓰는 편이 확실합니다. Bronze 영수증의 지문과도 같은 값이라 서로 맞춰 볼 수 있습니다.
</details>

<details><summary>Q3. 받은 파일의 지문을 다시 확인하는 이유는?</summary>

전송 중 파일이 잘리거나, 누군가 버킷의 파일만 바꿔 둘 수 있기 때문입니다. 실제로 합성 데이터가 원본을 덮어쓴 일이 있었습니다. 영수증과 다르면 그 파일로 만든 결과를 믿을 수 없으므로 멈춥니다.
</details>

<details><summary>Q4. MinIO가 사라졌는데 코드를 거의 안 고친 이유는?</summary>

boto3(S3 표준 API)로만 짰고 저장소 주소 · 키를 설정(.env)에서 받기 때문입니다. SeaweedFS도 같은 S3 API를 지원하므로 코드는 그대로이고, 띄우는 이미지만 바꾸면 됐습니다. 나중에 AWS S3로 옮길 때도 마찬가지입니다.
</details>
