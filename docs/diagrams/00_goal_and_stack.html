00포트폴리오 목표와 기술 선택

금융권 데이터 엔지니어 포트폴리오로 무엇을, 어떤 기술로, 왜

공모전 분석(01~05)은 이 포트폴리오의 '업무 사례'입니다. 핵심은 그 분석을 매월 자동으로 수집 · 적재 · 검증 · 제공되는
데이터 파이프라인으로 만드는 것이고, 기술마다 "왜 이것을 골랐는지"를 설명할 수 있게 정리했습니다.

목표 직무 · 금융권 DE
은행 · 카드사 데이터 엔지니어
최종 목적

공모전 카드 소비 분석을
매월 자동으로 재현 · 검증되는 데이터 마트 파이프라인으로

"분석하면서 직접 겪은 재현 불가 · 형식 불일치 · 수작업 검증 문제를
데이터 엔지니어링으로 해결했다" — 면접에서 말할 한 문장

완성되면 이렇게 동작합니다
  1. docker compose up 한 번으로 DB · 저장소 · Airflow · 대시보드가 뜸
  2. Airflow가 매월 원천을 수집해 원본 보관소에 기준월별로 저장
  3. dbt가 raw → staging → mart로 변환하고 품질 · 정합성 검사
  4. 검사를 통과하면 대시보드에서 Stress · 4유형 조회, 실패하면 알림
  5. 코드를 올릴 때마다 GitHub Actions가 합성 데이터로 전체를 검증
재현성원본 없이도 합성 데이터로 누구나 같은 결과를 실행
정합성원천 합계 = 마트 합계를 매번 자동 대사
자동화월 배치 · 과거 기간 재처리 · 실패 재시도
보안원본 비공개 · 인증정보 분리 · 소규모 셀 마스킹

처리 로직
Phase 1 · 사용 중		 Python · pandasNumPy · SciPy 이미 분석 로직이 pandas로 만들어져 있고, 원본으로 발표 결과 6/6 재현까지 확인 → 앞으로 SQL로 옮길 때 정답지(기준 구현)로 씁니다. Spark 대신 · 데이터가 약 24만 행이라 분산 처리가 필요 없음. 규모에 맞는 도구를 고르는 것도 설계 판단. 배치 스크립트 · 데이터 가공의 표준 언어
테스트
Phase 1 · 사용 중		 pytest단위 + 전체 실행 38개 손계산 값과 비교해 계산이 맞는지, 코드를 바꿔도 결과가 그대로인지(회귀) 자동 확인합니다. unittest 대신 · 문법이 짧고 여러 입력을 한 번에 검사(parametrize)하기 쉬움. 변경 전후 검증 · 회귀 테스트
수집 · 적재
합성 데이터
Phase 2		 NumPy 생성기시드 고정 공모전 원본은 재배포할 수 없어서, 형식과 분포를 흉내 낸 가짜 데이터로 누구나 실행할 수 있게 합니다. 원본 공개 대신 · 저작권 · 재식별 위험. Faker 대신 · 이름 · 주소가 아니라 숫자 분포만 필요. 개인정보 때문에 운영 데이터를 개발에 못 쓰는 환경 → 테스트 데이터 생성
수집
Phase 2		 requestsKOSIS · NAVER API 인구 데이터를 파일로 내려받던 수작업을 API 수집으로 바꾸고, 재시도 · 호출 제한 처리와 멱등성(다시 받아도 같은 결과)을 보장합니다. 수동 다운로드 대신 · 매월 반복 불가, 어떤 파일을 썼는지 기록이 남지 않음. 대외기관 데이터 연계 배치
원본 보관
Phase 2		 MinIOS3 호환 객체 저장소 받은 원본을 수정 없이 기준월별 폴더로 보관해, 문제가 생기면 그 달만 다시 처리할 수 있게 합니다. 로컬 폴더 대신 · S3와 같은 방식이라 클라우드로 옮겨도 코드가 거의 그대로. AWS S3 대신 · 로컬에서 무료. 원본 데이터 보존 · 데이터 레이크의 landing 영역
저장 · 변환 · 품질
데이터 웨어하우스
Phase 3		 PostgreSQLraw · staging · mart 스키마 계층별 스키마와 표준 SQL로 마트를 만들고, 서버형 DB를 운영 · 설계하는 경험을 보여줍니다. DuckDB 대신 · 가볍지만 서버 · 권한 · 동시 접속 같은 운영 요소를 보여주기 어려움. 금융권 RDB(Oracle 등)와 같은 SQL · 스키마 설계
변환
Phase 3		 dbtSQL 모델 관리 Phase 1의 함수 하나를 SQL 모델 하나로 옮기고, 계보(lineage) 문서와 테스트를 자동으로 만듭니다. 파이썬 스크립트 · 저장 프로시저 대신 · 어떤 표가 어떤 표에서 왔는지, 무엇을 검사했는지 관리가 어려움. 데이터 마트 표준화 · 변경 이력 관리
품질 · 정합성
Phase 3		 dbt tests+ 대사 쿼리 빈 값 · 허용값 · 지역코드 검사, 6개월 완전성, 원천 합계 = 마트 합계 대사를 매번 자동 실행합니다. 노트북에서 눈으로 확인 대신 · 실제로 '20대미만' 이름 불일치를 merge 후에야 발견했던 경험. 정합성 검증 · 대사 (금융 데이터의 핵심)
운영 · 제공
실행 관리
Phase 4		 Airflow월 배치 DAG 수집 → 적재 → 변환 → 검사 → 제공의 순서 · 재시도 · 과거 기간 재처리(backfill)를 한곳에서 관리합니다. cron 대신 · 작업 간 의존 관계, 실패 지점 재실행, 실행 이력 확인이 안 됨. 일 · 월 배치 스케줄 운영
실행 환경
Phase 2~4		 Docker Compose DB · 저장소 · Airflow · 대시보드를 명령 한 번으로 같은 구성으로 띄웁니다. 각자 설치 대신 · 버전 · 설정 차이로 "내 컴퓨터에선 되는데" 문제가 생김. 망분리 · 폐쇄망에서도 같은 구성 재현
자동 검증
Phase 4		 GitHub ActionsCI 코드를 올릴 때마다 테스트와 합성 데이터 전체 실행을 자동으로 돌려, 깨진 변경이 합쳐지지 않게 합니다. Jenkins 대신 · 저장소와 바로 연동되고 별도 서버가 필요 없음. 배포 전 검증 · 변경 관리
제공
Phase 4		 Streamlit조회 화면 마트 결과(Stress · 4유형 · 방어형 고객)를 파이썬만으로 빠르게 보여줍니다. 핵심은 파이프라인이라 화면은 가볍게. Superset · Tableau 대신 · 설치 · 설정이 무겁고 포트폴리오의 초점이 BI가 아님. 현업 조회용 데이터 제공
보안
전 단계 · 사용 중		 환경변수 · .gitignore+ 집계 마스킹 API 키는 코드 밖(.env)에, 원본 · 결과 파일은 저장소 밖에 두고, 공개 결과는 집계 · 마스킹된 값만 냅니다. 코드에 키 직접 작성 대신 · 실제로 노트북 공개 전 키를 지우는 스크립트가 필요했던 경험. 개인정보 보호 · 가명정보 처리
